# 2026-10-29 覆盖率实证

**上下文**：项目已经有 565 个测试全绿、总覆盖率 71.99%，看起来健康。但用户问了一句「测试覆盖率如何了，要验证的，不要写了很多没有验证大家都没有办法使用」。这句话点中了一个真问题：数字好看不等于核心链路被验证过。

## 意图

搞清楚三件事：真实覆盖率是多少、低的那些文件为什么低、能不能把它们补上且真的验证到。

## 输入

```bash
cargo llvm-cov nextest --config-file /tmp/nextest-fast-timeout.toml --summary-only
```

前提条件：

- 本机 shell profile **导出了真实的 `WECHAT_APPID` / `WECHAT_SECRET`**（当时没意识到，后面成了最大坑）
- `cargo-llvm-cov` + `cargo-nextest` 已安装
- 沙箱里 `cargo test --lib` 全量会挂起，必须走 nextest 配快速超时

## 输出

总覆盖率 71.99%，565 测试全绿。按文件拆开：

```text
wechat.rs         40.1%
push.rs           43.6%
cdp.rs            24.1%
push_browser.rs   22.2%
publish_steps.rs  12.0%
publish.rs         1.57%
```

## 解释

一开始以为"核心模块忘了写测试"。读了 `src/wechat.rs` 才发现不是。

原因：`WechatClient` 把 `https://api.weixin.qq.com` 写死在每个方法里，**没有任何注入点**。所以 `wechat.rs` 里原本那 15 个测试，全部只能测一件事——把 JSON 字符串丢给解析函数看返回值。没有一个测试真的调用过 `create_draft` 或 `upload_image`。

这正是「写了很多没有验证」的字面意思：测试存在，断言也在，但它们测的是字符串，不是行为。

## 问题

两个卡点。

**卡点一：无法注入出口。**

> 现象：所有微信 API 方法的 URL 都是常量拼接，测试无法把它指向本地服务。

**卡点二：连本地服务也打不通。**

> 现象：即使把 base URL 指向 `http://127.0.0.1:18878`，请求依然失败。

排查后确认：`proxy_url_for()` 对所有 `http://` URL 都会套上 `HTTPS_PROXY`，于是发往 `127.0.0.1` 的请求被推到代理，返回 502。**本地回环地址不该走代理。**

## 怎么解决的

1. 给 `WechatClient` 加 `with_base_url()`，并支持 `WECHAT_API_BASE` 环境变量覆盖。域名从常量变成数据。
2. 新增 `src/mock_wechat.rs`：只用 `std::net::TcpListener`，零依赖，按序应答并记录每一个收到的请求。测试因此可以断言"真实发出的 path 和 body 是什么"。
3. `proxy_url_for()` 加回环旁路，`127.0.0.1` / `localhost` 不再走代理。
4. 把推送管线抽成 `push_wechat_draft_with_client()`，客户端作为参数注入，让「渲染 → 取 token → 传图 → 建草稿 → 写 media_id → 归档 → 自动发布」整条链路可以在无浏览器、无凭证的条件下跑完。
5. 新增 28 个测试：18 个客户端方法级、5 个管线端到端、5 个 XPath 字面量转义。
6. 加 `scripts/coverage.sh` 和 CI `coverage` job。

覆盖率变化：

| 文件 | 修复前 | 修复后 |
| --- | --- | --- |
| `wechat.rs` | 40.1% | 93.6% |
| `push.rs` | 43.6% | 70.9% |
| 合计 | 72.0% | **74.2%** |

## 问题（第二轮）：自己引入两个回归

重构完本地全绿，推上去 CI 红了两次。

**第一次**（`e5ef3a4`）：抽出 `push_wechat_draft_with_client` 时，客户端构造跑到了 `draft.json` 校验之前。结果无草稿时报的是 `MissingEnvVar(WECHAT_APPID)`，而不是应该报的 `NoDraftJson`。

```text
FAIL push_json_fails_with_no_draft_before_network
```

**第二次**（`191d2f7`）：只把校验顺序改回来，渲染逻辑还留在内层函数里。于是构造客户端仍然在前，`push --render` 在没有凭证时不再产出 `draft.json`。

```text
FAIL push_auto_render_creates_draft_json
```

**共同根因**：本机 shell 导出了真实的 `WECHAT_APPID` / `WECHAT_SECRET`，CI 没有。本地绿、CI 红，查了两轮才想到是环境差异，不是代码差异。

修法：把「校验草稿 → 需要就渲染」整体提到凭据处理之前，让渲染不依赖客户端。

验证方式改成 CI 等价环境：

```bash
env -u WECHAT_APPID -u WECHAT_SECRET cargo nextest run --config-file /tmp/nextest-fast-timeout.toml
```

结果：593/593 通过，74.19% 行覆盖。

## 真实二进制冒烟（关键证据）

单测跑通不代表二进制能用。另写了一个 Python 假微信服务，用**真实 CLI** 跑完整流程：

```bash
moonpub --articles /tmp/msmoke2 new "端到端验证"
moonpub --articles /tmp/msmoke2 render "Articles/drafts/端到端验证.md"
WECHAT_API_BASE=http://127.0.0.1:18878 moonpub --articles /tmp/msmoke2 push "Articles/drafts/端到端验证.md"
```

假服务收到的请求：

```text
GET  /cgi-bin/token
POST /cgi-bin/draft/add
```

输出 `media_id: MEDIA_E2E`，`Articles/ready/端到端验证.media_id` 落盘，`status.jsonl` 记为 `ready`。

**同一轮也把边界暴露出来了**：CLI 走到浏览器自动化那一步时，真的连上了线上公众号后台，列出了 10 篇历史草稿，然后因为假草稿不存在输出了：

```text
⚠ automation: draft list edit button not found
```

这说明 `publish.rs` / `publish_steps.rs` / `cdp.rs` / `push_browser.rs` 那约 2700 行**无法用单元测试覆盖**，只能靠人工过闸。这一点已经明确写进 `docs/TEST_COVERAGE_ZH.md`，不用假测试去糊数字。

浏览器自动化部分仍是 7%–27%。两条路：接一个 CDP 回放层（工作量大），或者承认它只能人工验证。当前选择后者，并把边界写进文档，而不是用假测试凑一个好看的数字。
