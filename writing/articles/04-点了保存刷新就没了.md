上篇讲完"Vue 不认 JS 点击"，我以为最难的一关过了。结果一周后（2026-07-26 晚上）我撞上更隐蔽的一个坑：

配置了原创声明、赞赏、创作来源，每一项都点了开关、点了保存。退出编辑器，再进来——**全没了，回到默认**。

那种感觉特别窝火：你明明点了，界面也变了，刷新却像什么都没发生。这不是玄学，是四层根因叠在一起。那天晚上四个提交把这件事说透了，第一个提交 `e22f34a`（18:49）的 commit message 直接列了四层：

```text
Root cause (4-layer):
  steps only verified clicks not effects;
  hidden 未声明/已声明 DOM blocks fooled textContent state reads;
  global blind 确定 clicks hit wrong dialogs;
  configured settings were never saved to the draft before the browser closed.
```

我把它翻译成人话，就是下面四个坑。每一个我都踩过，每一个都以为"这次稳了"。


## 坑一：点了开关 ≠ 开关开了

最早那版 configure 的步骤，做完一件事只检查"我有没有点到那个按钮"。点到就打印 `✅`，然后进下一步。

问题在于：微信后台的开关点了之后，可能因为校验失败、可能因为点到了动画里还没生效的旧节点，**界面变了但后台没变**。我记的是"我点了"，不是"它真的开了"。

修复思路是把步骤改成**状态优先**：不靠"我点了"判断，而是读开关的真实状态。`step_yuanzhuang` / `step_zanshang` / `step_liuyan` 全部重写，先点、再读、读不到真实开启态就重试。这一步改的是"判断依据"——从动作日志换成效果事实。


## 坑二：textContent 会骗你

这是最阴的一个。微信在编辑器里同时塞了两套 DOM 块：一套"已声明"，一套"未声明"。**"未声明"那套永远在 DOM 里，只是 `display:none` 藏起来了。**

所以你用 `textContent` 读状态，永远能读到"未声明"三个字——因为它物理上存在，只是看不见。我前面好几次以为"原创没配上"，其实纯粹是被隐藏块骗了。

现在 `step_fucha` 用的 `FUCHA_SCRIPT`（publish_steps.rs:584）改成了看可见性：

```js
// #js_original_open 可见 = 已声明；未声明块永远藏在 DOM 里（display:none），
// 不能靠 textContent 里的"未声明"字样判断。
var open = document.getElementById('js_original_open');
```

一句话：**判断一个东西在不在，看它能不能被看见，别看它存不存在。**


## 坑三：全局搜"确定"，点到了别的弹窗

原创声明、赞赏、创作来源，每个都要在弹窗里点"确定"。最早那版是全局搜"确定"两个字然后盲点。

问题是：屏幕上可能同时叠着两三个弹窗，你搜到的第一个"确定"未必是你要关的那个。点错弹窗的确定，等于把别的操作提交了、把自己要做的操作关掉了。

修复是**弹窗作用域确认**——从你刚选中的 radio 逐层向上定位 picker，只在那个 picker 的 DOM 子树里找"确定/确认"，禁止全局盲点。代码里有专门的测试卡这条：`chuangzuo_confirm_is_scoped_to_picker`（publish_steps.rs:1129）断言脚本里必须含 `parentElement` 和 `input[type="radio"][value="4"]`。


## 坑四：保存按钮，根本没点到

前面三个坑修完，我以为稳了。然后发现最致命的一个：`configured settings were never saved to the draft before the browser closed`。

配置好的设置，从没在浏览器关闭前真正保存进草稿。为什么？因为**残留弹窗挡住了保存按钮**。

我前面开了一堆 picker（原创 picker、创作来源 picker），如果某个 picker 没关干净，它就浮在编辑器上。我点"保存为草稿"，坐标算出来是保存按钮的位置，但那个位置实际被 picker 盖住了——CDP 把鼠标点下去，点中的是 picker，不是保存。于是整轮设置白配。

`step_baocun`（publish_steps.rs:600）现在的注释把这件事写死了：

```rust
// 任何残留弹窗都会挡住保存按钮的点击（picker 未关曾导致整轮设置不落库），
// 保存前先关掉所有可见弹窗。
for _ in 0..3 {
    let closed = page.evaluate(CLOSE_VISIBLE_DIALOGS_SCRIPT)...;
    if closed == 0 { break; }
    println!("    关闭残留弹窗: {closed} 个");
}
```

`CLOSE_VISIBLE_DIALOGS_SCRIPT`（publish_steps.rs:312）按 `__close-btn` 把可见弹窗一个个关掉，最多三轮。关干净了，才用可信 CDP 坐标点击去点"保存为草稿"。按钮没找到就直接告警"后台设置可能仍未持久化"——不再假装成功。

配套的 `close_dialog`（cdp.rs:273）是兜底：先按 Escape，再依次点"取消"/"关闭"，专门对付那些关不掉的顽固弹窗。


## 真正的修复不是"再点一次"，是"验证它真的落库了"

前面四层，本质上都是同一个错误：**把"我执行了动作"当成"系统进入了目标状态"。**

最彻底的修法在 `step_fucha`（publish_steps.rs:525）——配置完、保存完，**重新加载编辑器，去读微信后台真正返回的状态**：

```rust
// 只信保存后的服务器状态：重载编辑器，读设置行的真实文案。
// 点击日志和内存态都可能是假成功（弹窗遮挡、校验拦截），重载后的
// 页面状态才是微信后台真正落库的结果。
let _ = page.evaluate("location.reload()").await;
for _ in 0..30 {
    sleep_ms(500).await;
    // 等 #js_original 出现，最多 15 秒
}
// 读 original / reward / source / comment 四个真实状态
```

重载之后逐项对：

- 原创：`declared` 开头才算"原创已落库"，否则 `⚠ 原创未保存到后台`
- 赞赏：状态不是"不开启"才算落库
- 创作来源：空字符串就 `⚠ 创作来源未保存到后台`
- 留言：`on` 才落库

**这一步把"我以为保存了"变成了"后台确实存了"。** 之前所有的坑，最后都靠这一道重载复核兜底——不管前面哪层没生效，这里都能抓出来告警，而不是静默失败。

## 带走的一句话

> 自动化最危险的不是报错，是"假成功"——动作执行了，状态没变，还没人发现。对付假成功，唯一靠谱的办法是：做完之后，去系统真实状态的地方再读一次。
