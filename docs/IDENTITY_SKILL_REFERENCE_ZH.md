# identity-skill 参考融合地图

这份文档记录 MoonPub 对 [Sac-Y/identity-skill](https://github.com/Sac-Y/identity-skill) 的参考结论。

结论先说清楚：

**identity-skill 对 MoonPub 的价值在于“参考图驱动的高保真视觉工作流”，不是让 MoonPub 近期变成个人网站生成器。**

## 参考库的核心启发

`identity-skill` 的定位是用 Codex / 图像生成 / 前端构建流程做个人网站。它的关键不是某段代码，而是这套阶段化设计纪律：

- 先锁定内容和风格，再出图。
- 参考图确认后才进入素材拆分。
- 素材拆分确认后才生成或整理素材。
- 素材评审通过后才开始写页面代码。
- 最终用参考图逐区 QA，并保留保真台账。

它对 MoonPub 有价值的地方是：

- 把“审美”变成可确认、可复查的中间产物。
- 把图片素材和代码边界先拆清楚，避免做成一整张死图。
- 用阻塞式确认保护用户，不让 Agent 一口气做完一个方向错的网站。
- 用品味校准避免默认 AI 科技感、模板感和无意义装饰。
- 用 QA 台账把“像不像”从主观印象变成逐区检查。

## 与 MoonPub 的映射

| identity-skill 能力 | 可吸收点 | MoonPub 对应落点 | 当前判断 |
|---|---|---|---|
| 内容与风格锁定 | 先明确目标、受众、内容充分性和视觉方向 | 未来官网 / 作者页 / 本地 App 首屏设计流程 | 可吸收为设计流程 |
| 参考图锁定 | 写代码前先确认视觉目标 | 未来封面模板、官网落地页、插件首页大改 | 适合高视觉成本任务 |
| 素材拆分清单 | 区分代码层、背景素材、前景素材、真实素材 | 封面生成、文章配图、本地 App / 网站素材 | 值得吸收 |
| 素材生成评审 | 生成图不直接进代码，先逐项验收 | 封面 / 配图 / 官网素材 QA | 值得吸收 |
| 高保真复刻与 QA | 逐区对照参考图、记录保真台账 | 未来官网、本地 App、插件首页视觉改版 | 中长期可用 |
| taste calibration | 干净、高端、受控、强排版、少 AI 默认套路 | MoonPub 排版主题、封面风格、官网视觉 | 已经部分方向一致 |
| reference asset splitter | 用交互性和可编辑性决定素材边界 | 微信 HTML、封面、官网构建 | 可作为设计原则 |

## 最值得吸收的三件事

### 1. 高视觉成本任务要有确认关卡

MoonPub 当前最容易出现反复返工的地方包括：

- 文章封面。
- 生活合集排版主题。
- 官网 / README 首屏素材。
- Obsidian 插件首页视觉改版。
- 未来本地 App 的 onboarding 和 dashboard。

这些任务不应直接进入实现。更稳的流程是：

1. 内容与风格简报。
2. 参考图或视觉 mock。
3. 素材拆分清单。
4. 素材评审。
5. 实现与视觉 QA。

这能避免“代码已经写了，但方向不喜欢”的返工。

### 2. 素材边界要先拆清楚

MoonPub 后续如果继续做封面、配图、官网或本地 App，不应该把复杂视觉一股脑烙成图片，也不应该把所有视觉都硬用 CSS 画。

推荐边界：

- 文字、导航、按钮、布局、可编辑标签留在代码层。
- 复杂纹理、摄影氛围、插画、真实照片和产品 mock 作为素材。
- 用户头像、真实 logo、产品截图等事实性素材不能擅自生成。
- 参考图只作为构建目标，不作为可裁切素材来源。
- 所有素材都要有最终路径、来源和替换状态。

这对微信公众号 HTML 同样重要：微信编辑器更偏好可编辑的 inline HTML，不能把正文排版退化成整张图。

### 3. 视觉 QA 要可复查

如果未来做官网或 App，不应只说“看起来差不多”。更好的验收材料是：

- 参考图路径。
- 渲染截图路径。
- 每个 section 的必须保留锚点。
- 字号、间距、素材占宽等关键几何对账。
- 已知偏差和原因。

这和 MoonPub 现有的 `docs/first-run-evidence/` 思路一致：视觉证据不散落在聊天里，而是归档成可复查材料。

## 不建议近期吸收的部分

短期不要把下面能力做进 MoonPub 主线：

- 通用个人网站生成命令。
- 大量内置个人主页模板。
- 默认依赖图像生成模型才能使用 MoonPub。
- 把参考图或生成图直接裁切成网站素材。
- 为官网 / App 引入重型前端框架，只为了复刻某个参考图。
- 在 v0.4.x / v0.5 阶段把重点从发布链路转向个人网站生成。

原因：

- 当前最重要的目标仍是让用户顺利完成 Obsidian / 飞书 / 照片 -> 草稿 -> 预览 -> 微信草稿。
- MoonPub 的核心不是个人网站构建器，而是本地发布内核。
- 视觉流程可以提升封面、排版、官网和插件首页，但不能成为基础发布流程的前置依赖。

## 对 MoonPub 路线的建议

近期仍按这个顺序推进：

1. 先补齐 v0.4.2 的首次体验证据和真实微信回归材料。
2. 再收 v0.5 插件化核心。
3. 如果要重做官网、插件首页或本地 App 首屏，再引入参考图驱动流程。
4. 如果要继续提升封面系统，先做“封面 brief -> 参考图/样张 -> 固定封面路径 -> 发布复用”的小闭环。
5. 不新增 `moonpub personal-site` 这类命令，除非 MoonPub 的产品边界已经明确扩展到作者主页生成。

一句话：

**MoonPub 可以学 identity-skill 的设计流程纪律，但不能学成一个泛化个人网站生成器。**

## 安全与边界备注

这类 skill 往往会要求强确认、素材生成、子 Agent 和前端写入。MoonPub 如果参考它，应保持：

- 不复制外部代码和内置模板。
- 不执行外部仓库脚本。
- 不把用户头像、身份资料、真实社交链接或未公开作品写入公开仓库。
- 不让 Agent 自动生成或篡改用户身份事实。
- 不把“视觉品味”写成可覆盖系统规则的隐性人格指令。
