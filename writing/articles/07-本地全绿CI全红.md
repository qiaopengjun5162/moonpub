2026-10-29 晚上 22 点多，我刚做完上一篇那套覆盖率改造——本地 `cargo nextest run`，**593 个测试全绿**，覆盖率 74.2%。

推上去，CI 直接双红。

`test` 和 `coverage` 两个 job 一起挂。第一个报错长这样：

```text
push::tests::push_json_fails_with_no_draft_before_network
expected NoDraftJson, got MissingEnvVar("WECHAT_APPID")
```

我盯着这行看了半天。本地明明全绿，怎么一上 CI 就变了？更奇怪的是——这个测试在我改之前是过的，我也没动它的断言。

## 第一次修：把校验提前（22:32）

病根是我自己刚下的手：为了让推送管线可以打 mock 测试，我把 `push_wechat_draft` 拆成了两半——外壳负责读凭据、建 client，内层 `push_wechat_draft_with_client` 负责真正的网络流程。

拆的时候我只想着"把网络半边变成可注入的"，没注意**顺序被改变了**：原来先检查 `draft.json` 在不在，再读凭据；拆完之后，client 先被构造，凭据先被读。

于是当一个 workspace 里还没有 `draft.json` 时：

- 改之前：报 `NoDraftJson`（"你还没渲染"）
- 改之后：报 `MissingEnvVar(WECHAT_APPID)`（"你没配 appid"）

错误类型变了，测试当然挂。

修复 `e5ef3a4`（22:32）很直接：把 `draft.json` 的存在性校验挪回凭据之前。

```rust
let draft_json = dir.join(format!("{slug}.draft.json"));
if !draft_json.exists() && !auto_render {
    return Err(AppError::NoDraftJson(draft_json));
}
```

跑测试，本地全绿。推送。

我以为完了。

## 第二次修：渲染也得提前（22:37）

**五分钟后**，CI 又红了。

这次挂的是另一个测试：

```text
push::tests::push_auto_render_creates_draft_json
assertion failed: draft.json should be created by auto-render
```

我才意识到第一次修只修了一半。

看那行条件：`if !draft_json.exists() && !auto_render`。当 `auto_render = true` 时，这个分支直接跳过——校验放行了，但**渲染动作还留在内层函数里**。而内层函数是在 client 构造之后才被调用的。

链条是这样的：

```text
外壳：读凭据 → 建 client  ← 这里就炸了
内层：缺 draft.json → 渲染 → 上传 → 建草稿
```

没有凭据，client 根本建不出来，`push --render` 连"渲染"这一步都走不到——它承诺的"没有 draft.json 就自动渲染"失效了。

修复 `191d2f7`（22:37）把「校验 + 渲染」整体前移，变成"先确保 draft.json 存在，再碰凭据"：

```rust
// Materialise draft.json before touching credentials or the network.
// Ordering matters twice over: a missing draft must fail as NoDraftJson
// rather than as a missing appid, and `push --render` must still write the
// draft on machines that have no credentials configured.
let draft_json = dir.join(format!("{slug}.draft.json"));
if !draft_json.exists() {
    if !auto_render {
        return Err(AppError::NoDraftJson(draft_json));
    }
    render_draft(articles_dir, &article, cfg)?;
}
```

同时把内层那个已经没用的 `auto_render` 参数删了——职责清了：外壳负责"把草稿准备好"，内层只管"把草稿发出去"。

这次推送，CI 绿了。

## 真正的根因：我的 shell 里有真凭据

两次修复都只是治了"顺序"，但有个更根本的问题我一直没问：

**为什么本地会全绿？**

如果是顺序错了，本地应该也挂才对。

答案在我自己的 shell profile 里：这台机器 `export` 了真实的 `WECHAT_APPID` / `WECHAT_SECRET`。

那个测试走的是 `push_article` → 先读凭据 → 凭据存在，顺利通过 → 再渲染 → 渲染成功 → 断言 `draft.json` 存在 → 通过。

**断言的是结果，而结果被本机环境变量偷偷满足了。**

CI 上没有这两个变量，同一段代码直接返回 `MissingEnvVar`，渲染根本没执行，断言自然失败。

这就是最难受的地方：测试没写错，代码在"有凭据"的世界里也确实对。**但测试通过的原因是环境凑巧，不是逻辑正确。**

## 验证：清掉凭据，才是 CI 等价

修复之后我没有直接信"本地绿了"，而是先清掉凭据再跑：

```bash
env -u WECHAT_APPID -u WECHAT_SECRET cargo nextest run
```

结果：**593/593 通过，74.19% 行覆盖**——和 CI 完全一致。

从那以后这条命令成了本项目的固定动作。`AGENTS.md` 里也写进去了。

## 防复发：三条规则

`ENGINEERING_LESSONS_ZH.md` 第 264 条把这件事记成了「本地有真实凭据，测出来的是『本机能跑』，不是『CI 能跑』」，防复发三条：

1. **本地验证必须清掉凭据跑一次**：`env -u WECHAT_APPID -u WECHAT_SECRET cargo nextest run`，这才是 CI 等价环境。
2. **任何依赖环境变量存在与否的分支，测试里要用 `env -u` 或显式注入来固定前提**，不要依赖"本机正好有"。
3. **结论以 CI 为准**，本地绿只说明"本机能跑"。

第一条是操作，第二条是设计，第三条是心态。第三条最难——它要求你承认：**自己机器上的绿灯，不算证据。**

## 带走的一句话

> "本地全绿"不是结论，是一个待验证的假设。当你的机器和 CI 的唯一差别是一个环境变量时，那个变量就是你最大的盲区。
