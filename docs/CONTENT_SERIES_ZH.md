# MoonPub 内容系列规划

这份规划服务于 MoonPub 的技术用户 Beta 推广。目标不是堆叠功能清单，而是帮助读者先理解价值、再完成第一次本地体验，最后才进入微信草稿和后台确认。

所有文章都遵循同一边界：不承诺无人值守自动发表；不展示或收集真实 token、二维码、AppSecret、账号或私人素材；只陈述已经验证的产品能力。

## 第一篇：项目介绍

**暂定标题：** 做一篇文章，自动跑到手机预览：我做了一个本地内容发布副驾驶

**目标读者：** 使用 Obsidian / Markdown 写作，或有飞书秒记、照片记录但没有稳定整理出口的人。

**要回答的问题：**

- What：MoonPub 是什么，不是什么。
- Why：为什么“写完后的一公里”值得自动化。
- Who：哪些人适合在当前 Beta 阶段使用。
- How：Markdown、飞书、照片怎样自动跑到本地预览和手机预览。
- Boundary：为什么最终发表始终由人确认。

**读者行动：** 打开 v0.4.2 release，安装后先运行 `moonpub doctor` 或打开 Obsidian 插件首页。

**稿件：** [MOONPUB_INTRO_ARTICLE_ZH.md](MOONPUB_INTRO_ARTICLE_ZH.md)

## 第二篇：把飞书秒记变成可修改的文章草稿

**核心场景：** 跑步、散步或临时想法说完后，转写不再停在飞书列表里。

**重点内容：**

- `Feishu Minutes -> Inbox -> Draft -> Preview` 的保守路径。
- 完整转写发送到 AI 前的确认，以及为什么默认不直接 push。
- 如何保留口语感和现场感，而不是把口述稿夸张地“润色成文章”。

**读者行动：** 从一条非敏感的秒记开始，只完成草稿和本地预览。

## 第三篇：让照片成为真实的生活记录，而不是自动生成的故事

**核心场景：** 同一天的一组照片，记录跑步、散步、旅行或日常。

**重点内容：**

- 默认只用元数据做素材整理，不臆测画面事实。
- 为什么视觉分析必须单独确认、为什么结果必须人工核对。
- 从照片目录到 `Inbox/Photos/`、草稿和本地预览的路径。

**读者行动：** 选一组照片做一篇仅在本地预览的生活素材稿。

## 第四篇：为什么 MoonPub 不做“无人值守自动发表”

**核心场景：** 解释自动化、隐私与作者责任之间的取舍。

**重点内容：**

- 微信扫码、验证码、审核和最终发表不能也不应绕过。
- 浏览器自动化的作用是辅助重复设置，不是接管账号。
- 本地 Markdown、草稿、预览和人工确认为什么是默认安全路径。

**读者行动：** 先在本地预览确认，再选择是否推进到微信草稿。

## 第五篇：如何把一篇公众号文章先在本地排好

**核心场景：** 减少在公众号编辑器里反复调样式的时间。

**重点内容：**

- 微信兼容 HTML、23 套主题、20 种 Block 和排版配方的定位。
- 本地预览与微信公众号后台手机预览不是同一个步骤。
- `layout-audit` 与 `preflight` 如何在不触达微信的前提下做发布前检查。

**读者行动：** 用已有 Markdown 文章生成一次本地预览，并在推进前检查排版质量门。

## 发布节奏

建议先发布第一篇项目介绍，再根据读者最常问的问题决定第二篇优先写飞书还是照片。每篇只保留一个明确的下一步动作，避免把下载、配置、AI、微信后台和所有高级命令同时压给第一次接触的读者。
