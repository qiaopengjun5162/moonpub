6 月 11 日晚上 8 点 31 分，我提交了一条看起来人畜无害的 feat：

```text
20:31  feat: publish 模块 — push 成功后自动打开后台编辑页
```

想法很朴素：文章推成草稿之后，自动把后台编辑页打开，省得我手动去点。我以为这是一两行代码的事。

这是我那天第 31 次提交，也是接下来三个半小时噩梦的起点。

## 先说结果，免得你以为我夸张

6 月 11 日这一天，我一共提交了 **87 次**——到今天仍是这个项目的单日最高纪录。

```bash
git log --format="%ad" --date=short | sort | uniq -c | sort -rn | head -1
#   87 2026-06-11
```

其中晚上 8 点 31 分到 11 点 57 分，三个半小时，连续二十多次提交，全部为了同一件事：**让"原创声明、赞赏、创作来源"这几个开关真的生效。**

开关点了，页面上该亮的不亮；脚本说"点成功了"，微信后台什么都没变。不报错，不崩溃，就是没用。

## 前两个小时：我以为问题在 DOM

头两个小时我打的全是 DOM 定位的 fix。微信后台的草稿列表不是普通列表——卡片上的"编辑"按钮是 hover 之后才出现的隐藏菜单，URL 里的 `vid` 和草稿真实 ID 不是同一个东西，登录页还会伪装成编辑页。

```text
20:34  feat: publish 集成 playwright-cli 后端自动化
22:25  fix: DOM 级登录超时检测 — 拦截微信假登录页面
22:32  fix: 首页自跳转获取动态 token — 根除 Cookie 被冲掉问题
22:40  fix: 草稿箱列表点击进入 — vid≠appmsgid 终极解决
22:44  fix: 先 Hover 卡片再找编辑按钮 — 微信隐藏式菜单
```

每修一个，我都以为"这下通了"，然后下一个冒出来。等到 22:44 那条"隐藏式菜单"修完，我终于能稳定地进到编辑器里。

问题才刚开始。

## 真正的战场：开关点不亮

进了编辑器，真正的麻烦是那几个开关。原创声明要勾一个"我已阅读并同意"，赞赏要开，创作来源要选。每一个，我都能用自动化"点"到，但微信后台就是不认。

我的第一反应是：**工具不行，换一个试试。**

于是 21 点 28 分，我把 Node 的 Playwright 换成了 Rust 的 `headless_chrome`，想彻底去掉 Node 依赖：

```text
21:28  feat: Rust headless_chrome 浏览器自动化 + PROGRESS 记账
```

到 23 点 08 分，我放弃了，提交信息写得很直白：

```text
23:08  refactor: publish 切回 Playwright Node — headless_chrome evaluate 有 bug
```

"evaluate 有 bug"——我以为找到了病根。回到 Node，继续打。

但 11 分钟后的 23 点 19 分，我又切回了 Rust：

```text
23:19  refactor: 纯 Rust XPath 点击 — 无 JS eval, CDP DOM 原生查询
```

到 23 点 57 分，最终形态：

```text
23:57  refactor: 纯 Rust CDP — find_elements + click(), 零 JS eval
```

**一百分钟，Rust → Node → Rust，两轮往返。** 每次切回去的时候，我都觉得"这回工具对了"；每次又切回来，我都觉得"那个库真不行"。

现在回头看提交记录，这一段最诚实的地方在于：它把我当时的焦虑完整留了下来。一个程序员在三个半小时里反复横跳，不是因为他在做实验，是因为他不知道病根在哪，只能换锤子。

## 第二天才找到病根

6 月 12 日我接着打。晚上 8 点，出现了这一条：

```text
20:01  fix: restore 赞赏 + 创作来源 to original working code from git history
```

`restore ... from git history`——翻译成人话就是：**我改崩了，从 git 历史里把之前能跑的版本捞回来。** 这是真实的开发状态，不是演示稿。当时的代码已经乱到我不相信自己能修好，只能让 git 当备份。

又过了 20 分钟，第一条点出根因的提交出现了：

```text
20:21  fix: 原创 checkbox use CDP click for 我已阅读并同意 (Vue ignores JS events)
```

括号里那句 **`Vue ignores JS events`**，是整场战役的钥匙。

微信编辑器是 Vue 应用。我用自动化派发的点击事件，是 JS 合成出来的，`isTrusted=false`。Vue 的模型层看到这种事件，直接忽略——它只认真人用鼠标产生的、浏览器内核派发的可信事件。

所以不是我的选择器错了，不是 Playwright 不行，也不是 headless_chrome 的 evaluate 有 bug。**是我在用一个框架根本不听的语言跟它说话。** 脚本"点了"，Vue 说"这不是人点的，我不理"。

后面几条都是在补这个认知：

```text
21:20  fix: use CDP clicks for 赞赏 + 创作来源 initial triggers (Vue ignores JS events)
21:28  fix: scroll to bottom after editor load to trigger Vue settings rendering
```

最后一条还暴露了另一个坑：Vue 的设置有部分是滚动到可视区才渲染的，不滚到底，连 DOM 都没有。这已经不是点击事件的问题了，是渲染时机。

## 我错在哪

这三篇文章里我最想让你带走的一句话：

**当一个症状在三个不同的库里都出现，问题大概率不在库，在你和它之间的那层协议。**

我花了一百分钟换技术栈，又花了一整个晚上 revert 代码，根因始终是同一个：Vue 不认合成事件。每换一次库，我都能短暂地"觉得有进展"，因为新库在某个具体选择器上确实比旧的顺手。但"开关不亮"这个核心症状，三次都没变。

如果当时我肯在第一次"点成功却不生效"时就打开 DevTools 看一眼事件的 `isTrusted`，可能半小时就结束了。我没有，因为换工具比承认"我其实不懂前端框架"容易。

这条现在写进了项目的 `AGENTS.md`，是整份文档最硬的一条约束：

> 微信编辑器是 Vue 应用。所有开关必须用 CDP 派发可信鼠标事件（先取坐标，再 `page.click(Point)`）。JS 合成点击 `isTrusted=false`，Vue 直接忽略。

它值三个半小时加一整个晚上。

## 你可以自己核对

这篇文章里每一个时间点都来自真实提交，复制就能跑：

```bash
# 06-11 当晚 20:31 → 23:57 的全部提交
git log --format="%H %ad %s" --date=format:"%H:%M" \
  --since="2026-06-11 20:00" --until="2026-06-12 00:00"

# 06-12 晚上从 restore 到 scroll-to-bottom 那一段
git log --format="%H %ad %s" --date=format:"%H:%M" \
  --since="2026-06-12 19:00" --until="2026-06-12 21:30"
```

第一条会列出从 `feat: publish 模块` 到 `refactor: 纯 Rust CDP` 的全部提交；第二条是 `restore ... from git history` → `scroll to bottom` 的 Vue 段。提交号和我文中写的一致。
