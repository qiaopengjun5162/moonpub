# 操作记录模板

复制下面整块，改掉占位内容。写不动就先填"意图"和"问题"两栏，其余回头补。

不要为了填满而编。某一栏当时确实没想清楚，就写"当时没想清楚，后来发现是……"——这比编一个漂亮的原因有价值。

---

````markdown
# YYYY-MM-DD 短标题

**上下文**：一句话说明当时在做什么、为什么现在做这件事。

## 意图

想达成什么。用动词开头，说清目标状态。

## 输入

涉及文件、命令、前提条件。

```bash
# 实际跑的命令，原样贴
```

前提条件（很重要，环境差异往往是 bug 根因）：

- 本机 shell 是否导出了某些环境变量
- 依赖的版本、工具是否已安装
- 网络/代理状态

## 输出

实际发生了什么，原样贴关键输出，不要复述。

```text
# 报错、测试结果、命令输出，原样
```

## 解释

为什么会得到这个输出。允许写错，后来发现推翻就回来补一行。

## 问题

卡在哪。一句话说清现象。

> 现象：……

## 怎么解决的

尝试过什么，哪条路走通了，哪条路走死了。走死的也要写——那是别人最想避开的。

1. 试了 A，结果……
2. 换成 B，结果……
3. 最终 C，因为……

## 证据

- 提交：`xxxxxxx`
- CI run：`xxxxxxxx`
- 截图：`writing/assets/YYYY-MM-DD-主题-01-说明.png`
- 复算命令：`...`

## 能写成什么

一句话：这段经历可以支撑哪篇文章的哪个部分。

## 还有没解决的

诚实列出。没有就写"无"。
````

---

## 填写示例

一个合格的"问题"栏长这样：

> **现象**：本地跑测试全绿，推上去 CI 红。两次都是同一个测试。

一个不合格的：

> **问题**：有点小问题，已经解决了。

差别在于：前者能让另一个遇到同样现象的人立刻对上号，后者什么也留不下。
