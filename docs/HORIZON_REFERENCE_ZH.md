# Horizon 参考融合地图

这份文档记录 MoonPub 对 [Thysrael/Horizon](https://github.com/Thysrael/Horizon) 的参考结论。

结论先说清楚：

**Horizon 对 MoonPub 的价值在于“多源信息进入写作系统前的雷达、筛选、评分、溯源和日报流水线”，不是让 MoonPub 近期变成新闻抓取平台、邮件分发系统或自动资讯站。**

## 参考库的核心启发

Horizon 的公开定位是面向每日精选 AI 新闻的自动化系统。它的核心链路大致是：

- 从多源新闻、RSS、社媒或 API 抓取信息。
- 对内容去重、过滤和聚类。
- 用 AI 做重要性评分、摘要和背景补全。
- 生成结构化 Markdown / 页面 / 邮件或通知。
- 通过定时任务持续运行，形成每日信息流。

MoonPub 不应该照搬这条链路，但它给了我们几个很有价值的产品原则：

- 素材进入文章草稿前，先做来源、重复度和重要性判断。
- AI 摘要必须保留原始来源，不应把生成文本伪装成事实。
- 自动化日报应优先生成本地草稿和证据，不直接发布。
- 定时抓取和主动分发风险更高，应晚于手动输入源和本地预览。
- 信息流系统需要“可解释为什么选中”，不能只给最终文章。

## 与 MoonPub 的映射

| Horizon 能力 | 可吸收点 | MoonPub 对应落点 | 当前判断 |
|---|---|---|---|
| 多源抓取 | 输入源统一进入素材池 | `Inbox/`、未来公众号 URL / RSS / 读书摘录 | 只做长期研究 |
| 去重与聚类 | 同一事件/主题合并 | `radar`、未来 `preflight` / `draft-audit` | 值得吸收 |
| AI 评分 | 素材重要性、可写性排序 | `radar suggest`、文章选题建议 | 可吸收原则 |
| 背景补全 | 给素材补上下文 | `draft-from-inbox` 前的只读素材卡 | 谨慎使用 |
| Markdown 日报 | 结构化输出保留来源 | QunMind 日报、`compact-links` 来源索引 | 已部分一致 |
| 定时任务 | 自动生成候选日报 | 未来本地自动化 / 提醒 | 不进 v0.4.x / v0.5 |
| 邮件/站点分发 | 多渠道分发 | MoonPub 多平台发布长期方向 | 低优先级 |

## 最值得吸收的四件事

### 1. 素材先进入雷达，不直接变文章

MoonPub 现在已经有 `radar`、`Inbox`、飞书和照片入口。Horizon 的启发是：未来更多输入源进来后，不要急着全都生成文章。

更稳的路径是：

1. 素材进入 `Inbox/`。
2. 记录来源、时间、标题、URL、摘要和原始片段。
3. 做去重、聚类、重要性和可写性判断。
4. 输出候选清单和理由。
5. 用户确认后再生成草稿。

这能避免 MoonPub 变成“什么都抓、什么都写”的噪音机器。

### 2. AI 评分要可解释

如果后续 MoonPub 做选题雷达或日报候选，不应只给一个分数。更好的结构是：

- 为什么选中。
- 和哪些已有素材重复或相关。
- 适合写成什么类型：快讯、观点、教程、生活记录、日报条目。
- 原始来源是什么。
- 哪些信息只是推断，哪些来自原文。

这和 MoonPub 当前“草稿优先、证据优先”的方向一致。

### 3. 日报输出必须保留来源链

Horizon 的日报形态提醒我们：日报不是纯生成文案，而是“素材 -> 摘要 -> 来源”的可追踪产物。

MoonPub 后续做 QunMind 日报、公众号归档、热点选题或读书摘录时，应继续保持：

- 原文 URL 或本地文件路径保留。
- `compact-links` 或类似 block 作为唯一清晰来源索引。
- 摘要和评论区分开。
- 本地 Markdown / HTML 预览先于微信草稿。
- 用户确认后才推进到发布链路。

### 4. 自动化只能生成候选，不自动最终分发

Horizon 适合每天自动运行，但 MoonPub 的边界更敏感：它连着公众号、个人表达、付费合集和真实发布。

因此如果未来做定时雷达，应坚持：

- 可以自动抓取候选。
- 可以自动生成本地日报草稿。
- 可以提醒用户检查。
- 不能自动 push 到微信草稿，除非用户显式触发。
- 永远不能自动最终发表。

## 不建议近期吸收的部分

短期不要把下面能力做进 MoonPub 主线：

- 大规模新闻抓取。
- 默认 RSS / 社媒订阅扫描。
- 自动每日邮件分发。
- 自动生成并发布资讯站。
- 后台常驻定时任务。
- 把抓取、总结、分发包装成无人工确认的流水线。
- 默认联网补全背景和改写事实。

原因：

- MoonPub 当前最重要的目标仍是让 Obsidian / 飞书 / 照片 -> 草稿 -> 预览 -> 微信草稿稳定可用。
- 主动抓取和定时分发会引入版权、事实准确性、来源可靠性和平台风控问题。
- 用户当前更需要可控发布内核，而不是无边界资讯自动化。

## 对 MoonPub 路线的建议

近期仍按这个顺序推进：

1. 继续补 v0.4.2 首次体验证据和真实微信回归材料。
2. 保持 `radar` 作为选题辅助，不让它直接触发发布链路。
3. 如果要增强雷达，先做只读 `radar digest` / `radar candidates`，输出候选、理由和来源。
4. 如果要做日报，先让日报进入本地草稿和预览，不默认推微信。
5. 如果要接 RSS / 公众号 URL / 读书摘录，也先进入 `Inbox/`，统一走去重、来源索引和草稿确认。

一句话：

**MoonPub 可以学习 Horizon 的“多源素材 -> 去重评分 -> 来源保留 -> 本地日报草稿”纪律，但不能把发布工具变成自动资讯分发机器。**

## 安全与边界备注

MoonPub 后续如果参考 Horizon 做雷达或日报增强，应保持：

- 不抓取需要登录、Cookie 或绕过验证的内容。
- 不把生成摘要当作事实来源。
- 不默认下载或重分发受版权保护的全文。
- 不自动邮件群发或站点发布。
- 不把用户私有 Inbox 内容上传到第三方服务。
- 不让定时任务触发微信 API、浏览器自动化或最终发表。
