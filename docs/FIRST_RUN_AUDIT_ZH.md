# MoonPub 首次使用审计

这份文档不是愿景，也不是使用教程。

它只回答一个问题：

**截至当前代码状态，MoonPub 的“第一次使用体验”到底已经打通到什么程度，还有哪些地方只是实现了、但证据还不够强。**

目标是把“整体评估 -> 设目标 -> 生成计划 -> 逐步实现”的结果收成一份可复查基线，避免后面又回到“感觉做了很多，但不知道哪些是真的打通了”。

## 审计范围

本轮只审计第一次使用最关键的三条入口：

1. 当前文章入口
2. 飞书素材入口
3. 照片素材入口

同时把插件首页视为第一次体验的统一入口层。

## 审计结论

当前可以给出一个比较明确的结论：

- **MoonPub 已经不只是“命令集合”**，而是在形成一个多输入源的本地发布内核
- **飞书路线当前不建议拆独立项目**，更适合作为 MoonPub 内部正式模块继续推进
- **Agent 方向当前也不建议另起炉灶**，更合理的做法是继续把 MoonPub 包装成 Agent-ready 的本地发布内核
- **首次使用体验已具备真实路径证据，仍需在 Beta 试用中继续验证不同用户环境**
  - 当前文章入口：本地体验最稳
  - 飞书入口：证据最强，已经有真实闭环验证
  - 照片入口：产品形态、插件入口和真实本地草稿路径均已验证

## 审计标准

本轮审计只把下面这些当成强证据：

- 真实运行命令结果
- 已记录的真实闭环验证
- 现有插件代码能力
- 现有 app 级行为测试
- 最新文档入口是否与真实代码一致

只要某条路径还没有真实运行证据，就不能把它写成“已经彻底打通”。

## 路径 1：当前文章入口

### 当前目标

让第一次使用的人可以从：

`插件首页 -> 检查当前文章 -> 预览当前文章`

快速理解 MoonPub 的基本节奏。

### 当前状态

**已基本打通。**

### 强证据

- 插件首页现在已经有：
  - `查看整体文章池状态`
  - `检查当前文章状态`
  - `预览当前文章`
- `workspace --json`、`check --json`、`preview` 都已经是正式协议层
- 插件工作区工作台已经开始承担首页角色
- 当前文章工作台已经可以展示：
  - `has_html`
  - `has_draft_json`
  - `has_media_id`
  - `next_command`
  - `next_step`

### 审计判断

这条路径的风险最低，最适合继续作为第一次体验的“第一个入口”。

### 剩余缺口

- 当前还没有把“当前文章入口”的首次使用截图或 walkthrough 证据单独固化
- 仍然更多依赖文字说明，而不是更可视化的首次体验材料

## 路径 2：飞书素材入口

### 当前目标

让第一次使用的人可以从：

`插件首页 -> 导入最近飞书妙记 -> 草稿 -> 本地预览 -> 微信草稿`

顺着走下去。

### 当前状态

**三条首次入口里证据最强。**

### 强证据

- 2026-07-01 已有真实 CLI 闭环验证：
  - `moonpub --articles "<path>" --json intake feishu --latest --draft --preview --no-open`
  - `moonpub --articles "<path>" --json intake feishu --latest --draft --push`
- 已真实验证到：
  - `Inbox/Feishu`
  - `Articles/drafts`
  - 本地 HTML 预览
  - 微信草稿创建
  - 微信后台自动完成原创 / 赞赏 / 留言 / 创作来源 / 预览发送
- 插件层已补齐：
  - 飞书素材入口命令
  - 结果工作台中的显式“打开草稿”动作
  - 飞书结果工作台
  - 结果工作台后续动作按钮
- `intake feishu ... --draft --preview --json` 已有 app 级行为测试

### 审计判断

飞书路线已经不再只是“可选功能”，而是：

**MoonPub 当前最成熟的一条正式输入工作流。**

这也是为什么当前更合理的战略结论仍然是：

**先作为内部正式模块继续推进，不拆新项目。**

因为它最强的价值仍然依赖 MoonPub 的草稿、预览、推送和后台链路。

### 剩余缺口

- 已补真实插件首页、飞书结果页和草稿打开证据；仍需在 Beta 试用中观察不同用户的飞书授权、CLI 安装和 Obsidian 环境差异

## 路径 3：照片素材入口

### 当前目标

让第一次使用的人可以从：

`插件首页 -> 导入当前图片目录 -> 草稿 -> 本地预览`

快速把一组生活照片沉淀成草稿。

### 当前状态

**产品形态已明确，入口已到位，但真实闭环证据还弱于飞书。**

### 强证据

- `intake photos <file-or-dir> [--draft] [--preview] [--push]` 已正式落代码
- `Inbox/Photos` 统一元数据已到位：
  - `source: photos`
  - `type: photo-note`
  - `external_id`
  - `captured_at`
- `intake photos ... --draft --json` 协议已单独命名为 `intake-photos`
- `intake photos ... --draft --preview --no-open --json` 已有 app 级行为测试
- 插件层已补齐：
  - 当前图片所在目录入口
  - 结果工作台中的显式“打开草稿”动作
  - 结果工作台
  - 与飞书一致的后续动作串联

### 审计判断

照片路线已经具备成为第二条正式输入工作流的条件，但目前它更接近：

**“产品入口已成形，真实插件路径证据已归档，下一步进入 Beta 试用验证”。**

### 剩余缺口

- 已有真实照片目录到草稿、HTML 预览、结果工作台和草稿打开证据
- 默认路径仍然只使用文件路径、文件大小和修改时间；像素级理解必须继续保持显式确认和人工核对

## 插件首页审计

### 当前目标

让第一次使用的人不需要先记住全部命令，而是先从一个统一入口进来。

### 当前状态

**已经开始承担首页角色。**

### 强证据

- `查看整体文章池状态` 已从状态查询扩展为工作区工作台
- 工作区工作台当前已提供快捷入口：
  - 检查当前文章
  - 预览当前文章
  - 导入最近飞书妙记
  - 导入当前图片目录
- 工作区工作台已经有第一版上下文感知推荐：
  - 当前打开 Markdown 时，优先引导检查和预览当前文章
  - 当前打开图片时，优先引导导入当前图片目录
  - 当前没有打开文件或打开其他文件时，提示先选择更合适的入口
- 工作区工作台会按当前上下文展示“首次建议”步骤，而不是只罗列静态按钮
- `workspace --json` 继续作为这层首页的高层协议对象

### 审计判断

插件已经不再只是“命令壳”，而是在开始形成：

**一个首页式入口层。**

更准确地说，插件首页已经从“状态弹窗 + 按钮入口”推进到：

**能根据当前打开文件给出基础路径判断的首次体验工作台。**

### 剩余缺口

- 首页当前仍然是工作台弹窗，不是更稳定的持久页面或面板
- 上下文感知推荐已有第一版，但还缺真实截图或短录屏证明用户能看懂并顺着走
- 还没有把首页工作台、当前文章工作台、飞书结果工作台、照片结果工作台串成一段完整首次体验 walkthrough

## 当前首次体验验收结论

如果按“第一次使用是否已经值得让人试”来判断：

- 当前文章入口：`通过`
- 飞书入口：`通过，且是当前最成熟路径`
- 照片入口：`通过，默认元数据路径已完成真实插件证据`
- 插件首页：`通过，已有上下文感知推荐和真实体验证据`

## 当前仍然缺什么

当前最值得继续补的，不是再横向加很多新功能，而是下面这些证据和收尾项：

1. 飞书首次体验的截图或短录屏
2. 照片首次体验的真实样例验证
3. 插件首页上下文感知推荐的真实截图或 walkthrough 证据
4. 英文入口文档对首次体验的同步

## 对战略问题的结论回看

结合这轮首次使用审计，前面那两个关键战略判断仍然成立：

### 1. 飞书路线要不要拆独立项目？

当前结论：**先不要拆。**

原因：

- 它最强价值仍然依赖 MoonPub 主链路
- 当前更缺的是入口、体验和证据，而不是仓库切分
- 拆项目会把本来已经开始收口的入口层再次打散

### 2. 它能不能包装成 AI Agent 产品？

当前结论：**可以，但方式应是包装 MoonPub，而不是另起一个 Agent 仓库。**

原因：

- `workspace --json`
- `status --json`
- `check --json`
- `intake feishu ... --draft --json`
- `intake photos ... --draft --json`

这些协议层已经说明 MoonPub 正在长成 Agent-ready 内核。

## 下一步建议

如果继续按当前节奏推进，下一步优先级建议是：

1. 补真实首次体验证据
   - 飞书录屏 / 截图
   - 照片样例验证
2. 继续把插件首页做得更像真正首页
   - 上下文感知推荐
3. 再考虑把首次体验入口同步到英文对外材料

## 最终审计结论

当前最准确的说法不是“MoonPub 已经彻底产品化”，而是：

**MoonPub 已经完成了从命令集合向多输入源本地发布内核的关键转折，首次使用体验也开始从分散命令进入统一首页和正式工作流阶段。**
