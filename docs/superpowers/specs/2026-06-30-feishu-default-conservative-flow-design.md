# Feishu Default Conservative Flow Design

**Goal:** 明确飞书秒记进入 MoonPub 后的默认工作流：默认停在“可编辑草稿 + 本地预览”，只有用户显式要求时才继续推进到微信草稿。

## 背景

飞书秒记接入 MoonPub 之后，实际存在两类截然不同的使用场景：

1. **可直接推进的记录**
   飞书内容已经足够干净，用户希望尽快推进到微信草稿，再走公众号后台预览与发布。
2. **需要人工整理的记录**
   飞书内容只是原始输入，后续往往还需要：
   - 手工修改结构和措辞
   - 去掉 AI 味
   - 调整语气
   - 插入图片
   - 多次预览确认

对于第二类内容，如果系统默认自动推进到微信草稿，会让“草稿只是中间态”这件事变得不稳定，也容易造成用户误发。

因此需要在产品语义上先明确：**什么是默认路径，什么是显式加速路径。**

## 结论

默认策略采用：

**默认保守模式 + 显式直发开关**

也就是：

- 不带显式推进开关时，只推进到草稿和本地预览
- 只有用户明确要求，才继续推进到微信草稿

## 范围

本轮是**流程规则设计**，不是新的自动化实现。

### 包含

- 明确飞书链路的默认模式
- 明确快速直发模式的触发方式
- 明确与现有 `--preview` / `--push` / `configure` / `ship` 的关系
- 明确“本地预览”和“微信公众号后台预览”在工作流中的位置

### 不包含

- 新增 AI 判定逻辑
- 自动判断是否“可以直发”
- 按内容类型自动切换模式
- 改动 `ship` 的核心行为

## 设计原则

### 1. 默认先停在可编辑状态

飞书内容的默认去向不是“直接发”，而是：

1. 导入 Inbox
2. 生成可编辑草稿
3. 本地预览
4. 等待用户确认

这样能覆盖绝大多数真实使用场景，尤其是生活记录、随感、口述素材、跑步记录、照片配文等需要人工整理的内容。

### 2. 快速直发必须显式触发

快速模式不是系统猜测出来的，而是用户明确发出的指令。

当前最合适的显式触发方式就是已有的：

```bash
--push
```

即：

- `draft-from-inbox ... --push`
- `intake feishu ... --draft --push`

这意味着“继续推进到微信草稿”是一次有意识的决策，而不是默认副作用。

### 3. 本地预览与微信公众号后台预览分离

这是当前工作流里最容易混淆的地方，必须明确分层：

#### 本地预览

- 命令：`preview` 或 `intake/draft-from-inbox --preview`
- 作用：检查 HTML 排版、结构、文本、图片
- 阶段：还没进入微信草稿

#### 微信公众号后台预览

- 命令阶段：`configure` / `ship`
- 作用：把已进入微信草稿的内容发送到手机做后台预览
- 阶段：已经推入微信草稿之后

两者不互相替代。

### 4. 进入微信草稿后，后半段统一

无论内容来自：

- 本地 Markdown
- 微信读书笔记
- 飞书秒记

只要已经进入微信草稿，后半段流程就应该统一成同一套：

1. 微信草稿配置
2. 微信公众号后台预览
3. 人工发布

也就是：

`configure / ship -> 微信公众号后台预览 -> 发布`

## 两种标准模式

## A. 默认保守模式

推荐作为默认日常工作流。

### 命令形态

```bash
moonpub intake feishu --latest --draft --preview
```

或：

```bash
moonpub intake feishu --minute-token <token> --draft --preview --no-open
```

### 行为

1. 导入或更新 Inbox
2. 生成或更新草稿
3. 生成本地 HTML 预览
4. 停住，等待用户修改或确认

### 适用场景

- 闲月隐林类生活内容
- 原始口述较强的记录
- 需要去 AI 味
- 需要补图或删改
- 需要多次人工审阅

## B. 显式快速直发模式

仅在用户明确要求时使用。

### 命令形态

```bash
moonpub intake feishu --latest --draft --push
```

### 行为

1. 导入或更新 Inbox
2. 生成或更新草稿
3. 直接继续执行等价于 `push --render`
4. 推到微信草稿

### 适用场景

- 内容已经足够干净
- 本次就是想快速推进
- 用户明确知道自己不需要先停在本地预览

## 推荐规则

项目层面的推荐规则如下：

1. **默认永远走保守模式**
2. **只有显式加 `--push` 才进入快速模式**
3. **不要做自动猜测**
4. **不要根据内容长短或主观质量自动决定是否直发**

## 与现有命令的关系

### `--preview`

- 表示“先停在本地预览”
- 更适合作为默认飞书链路的主入口

### `--push`

- 表示“草稿生成后直接继续推进到微信草稿”
- 应继续保持显式开关语义

### `push --render`

- 仍然是“从本地草稿手动推进到微信草稿”的标准动作
- 默认保守模式下，用户确认后就走这一步

### `configure`

- 负责进入微信草稿后的公众号后台步骤
- 包括后台预览发送

### `ship`

- 仍然适合“已有成稿后的一键推进”
- 对飞书链路而言，不应取代“草稿先确认”的默认节奏

## 文档与产品表达要求

为了避免后续继续混淆，相关文档和说明要统一表达：

- 飞书内容默认先到“草稿 + 本地预览”
- `--push` 是显式继续推进
- 本地预览不等于微信公众号后台预览
- 一旦进入微信草稿，后半段就和其他文章完全一致

## 成功标准

满足以下条件即可认为这套规则被成功固化：

1. 用户能一眼理解默认模式和快速模式的区别
2. 用户不会再把本地 `preview` 和微信公众号后台预览混为一谈
3. 文档中明确写清“默认保守，显式 `--push` 才直发”
4. 飞书链路与项目其他文章在“进入微信草稿后”的后半段流程被统一描述
