2026 年 6 月 10 日晚上 8 点 07 分，我提交了第一个 commit。

```text
$ git show --stat 5a8bed0
 src/lib.rs                 | 3286 ++++++++++++++++++++++++++++++++++++++++++
 src/wechat.rs              |  331 +++++
 scripts/moonpub-backend.sh |  287 ++++
 docs/BROWSER_AUTOMATION.md |  169 +++
 README.md                  |   81 ++
 10 files changed, 4967 insertions(+)
```

一天，一个空目录，4967 行。

四个月后，`src/lib.rs` 只剩 131 行。

这两个数字之间的部分，就是这篇文章要讲的事。

## 先说痛点，因为它很具体

我平时在 Obsidian 里写东西，写完发公众号。问题不在写，在"发"。

文章正文已经在 Markdown 里了，但要真正变成一篇可发布的公众号文章，中间隔着这么一长串动作：

开后台 → 新建图文 → 粘贴正文 → 重新排版 → 上传图片 → 设封面 → 声明原创 → 勾协议 → 开赞赏 → 开留言 → 选创作来源 → 选合集 → 插模板 → 发手机预览 → 回后台确认 → 再同步到博客。

十几项设置，每项都要点几下。而且这些设置**每次都要重来一遍**，微信不会记住你上次的选择。

写得越多，这一步越烦。写到第二十篇的时候，我开始觉得，这活儿不应该由人干。

## 于是我一晚上写了 4967 行

那天晚上我的想法很简单：把整条链路用 Rust 重写一遍。

第一个提交里塞了六个模块：`render`（Markdown 转微信 HTML）、`push`（直调微信 API 建草稿）、`export`（导出 Zola 博客）、`preview`（本地打开）、`radar`（选题趋势）、`status`（状态跟踪）。附带 49 个单元测试，0 个 clippy warning。

提交信息最后一行写着：

```text
- 49 unit tests, 0 clippy warnings
```

当时我觉得这是一次很干净的起步。测试有了，lint 干净，功能齐了。

**但实际上这个提交里已经埋了一个错误，而且是我四个月后才承认的那个。** 先放一放，后面说。

## 真正的敌人不在 Rust 里

第一个提交那天（6 月 10 日）的晚上，我其实没碰浏览器。那一晚 33 次提交全是纯 Rust：Markdown 块模板、去 AI 味、封面 HTML、49 个测试、CI 和 Justfile。API 能把内容变成"草稿"，但那十几项后台设置——原创、赞赏、封面、合集——没有任何接口，只能在网页上点。

碰浏览器是**第二天**（6 月 11 日）的事。那天我一共提交了 87 次，是项目里最密的一天。从晚上 8 点 31 分到 11 点 57 分，三个半小时，我连续尝试了二十多次，只为了让"原创声明、赞赏、创作来源"这几个开关真的生效。

先看前两个小时，我在跟微信后台的隐藏 DOM 搏斗：

```text
20:34  feat: publish 集成 playwright-cli 后端自动化
22:25  fix: DOM 级登录超时检测 — 拦截微信假登录页面
22:32  fix: 首页自跳转获取动态 token — 根除 Cookie 被冲掉问题
22:40  fix: 草稿箱列表点击进入 — vid≠appmsgid 终极解决
22:44  fix: 先 Hover 卡片再找编辑按钮 — 微信隐藏式菜单
```

注意最后两条提交信息里的字眼：**「终极解决」「隐藏式菜单」**。

那不是修辞。那是当晚真实发生的事：我以为拿到的草稿 ID 就能直接跳转编辑器，结果 URL 里的 `vid` 和草稿真实 ID 根本不是同一个东西，直接跳必然 404。最后靠"先把鼠标悬停在卡片上唤出隐藏菜单，再点第二个按钮"绕过去了。

**这一天我第一次意识到：这个项目的难点不是 Rust，是逆向一个随时会变的前端。**

而真正的地狱在后面——为了让"原创/赞赏/来源"这几个开关生效，我在三个半小时里换了两轮技术栈：

```text
21:28  feat: Rust headless_chrome 浏览器自动化
23:08  refactor: publish 切回 Playwright Node — headless_chrome evaluate 有 bug
23:19  refactor: 纯 Rust XPath 点击 — 无 JS eval, CDP DOM 原生查询
```

根因后来才彻底搞清：**微信编辑器是 Vue 应用，JS 合成出来的点击事件 `isTrusted=false`，Vue 的模型直接忽略。** 脚本"点了"，页面上什么都没发生，也不报错。必须由 Rust 侧算出元素坐标，再通过 CDP 派发真正的可信鼠标事件。

这一条现在写在项目的 `AGENTS.md` 里，是整份文档最硬的一条约束。它值三小时的试错。

## 四个月后，我承认第一个提交是错的

回到那个 4967 行。

`src/lib.rs` 一个文件 3286 行，装了渲染、推送、导出、预览、趋势、状态六件事。当时我甚至有点得意——一个文件，一目了然。

四个月后，它变成了 131 行。

```text
$ wc -l src/lib.rs
     131 src/lib.rs
```

剩下的 3155 行去了哪？

去了 65 个文件。`cover.rs` 2415 行、`cli.rs` 2135 行、`app.rs` 1239 行、`publish_steps.rs` 1197 行、`push_browser.rs` 972 行……以及二十多个更小的模块。

这个过程不是一次重构完成的。第一次拆分发生在第二天：

```text
17:13  refactor: extract radar.rs from lib.rs (-1270 lines)
```

一次砍掉 1270 行。然后是 `protocol.rs`，然后在九月拆成 `protocol/` 目录。

**第一个提交错在哪？**

错在**把"一次能跑通"当成了"结构正确"**。

那天晚上它确实能跑。渲染、推送、导出都通了，测试也绿了。但 3286 行的单文件意味着：

- 任何一个改动，我都要在一个 3286 行的文件里定位
- 边界不存在，所以重复实现必然出现——后来我发现有 5 个地方各写了一份 HTML 转义，其中 3 份不转义单引号
- 测试只能测到最外层的函数，内部逻辑全部黏在一起

最典型的证据是：四个月后我抽出统一的 HTML 转义（提交 `ff64d47`），发现原来五份实现里有三份是**有 bug 的**——它们不处理单引号。这个 bug 在第一个提交里就存在了，一直活到十月。

一个 3286 行的文件，让这种 bug 有机会活四个月。

| 指标 | 数值 |
| --- | --- |
| 提交 | 479 次 |
| 其中修 bug | 163 次（34%） |
| 源码 | 29,298 行 / 65 文件 |
| 测试 | 593 个 |
| 发布 | 14 个版本，v0.1.0 → v0.4.8 |
| 封面风格 | 14 种 |

| 内置排版块 | 20 种 |

**这张表里我最想让人注意的是 34%。**

三分之一的提交是在修 bug。不是设计出来的架构，是一遍遍撞在微信后台的 DOM 上撞出来的。这个数字不好看，但它诚实。

## 所以这个系列要写什么

我打算把这个项目的完整过程写下来，从第一个提交开始。

不写"我用 Rust 做了一个工具"这种总结，而是写具体的东西：

- 那三个半小时到底试了什么，为什么前十九次都不行
- 微信后台的"保存"为什么点了不生效，要重载页面才能验证
- 我自己的两条改动，为什么本地全绿、CI 全红
- 覆盖率报告说 71.99%，为什么这个数字是假的

每一篇都会带上真实的提交号、命令输出和截图。你可以自己 `git log` 去对。
