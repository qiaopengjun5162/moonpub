# 订阅与直通：事件路由设计

本文记录一条事件路由的设计决策：**初始事件经由 Router 层创建 Worker 并建立订阅，同一 Thread 的后续事件直接发往该 Worker。**

这条决策来自 DeepSeek 产品部 Harness 团队《Super-agent 设计探索：迈向更自主的 Agent 系统》（2026-10-31，公众号「微信公众平台」）。它是该文第 3.2 节的核心机制，服务于第 2 节提出的「Router 层 + Worker 层」双层架构。本文在原文基础上重述并收敛，作为 MoonPub 的设计参考存档。

> 原文标题：Super-agent 设计探索：迈向更自主的 Agent 系统
> 作者/团队：DeepSeek 产品部 Harness 团队
> 发布时间：2026-10-31

## 设计目标

- 在「跨信道连续交互」与「多任务高并发」之间取得平衡：既要上下文连续，又要高吞吐。
- 避免全局 Router 节点成为系统瓶颈：已确定归属关系的后续事件不再逐条经 Router 转发。
- 让 Super-agent 在用户侧表现为「同一个 agent」，把 Session 当作实现细节，而不是用户的认知负担。

## 非目标

- 不要求每个 Thread 都永久占用一个 Worker。Worker 可以退订、交回 Router 重新分派。
- 不取消 Router 的全局可见性。Router 仍观测所有事件以掌握全局状态，只是不再逐条转发已订阅事件。
- 不依赖点对点通信解决 Worker 间冲突，而是通过共享 Thread 的订阅广播来发现冲突。

## 当前问题（为什么需要它）

双层架构把「维护全局连续性」（Router 层）与「高并发执行」（Worker 层）拆成两个职责层。但如果已分配任务的**每个后续事件**仍需经由 Router 层转发，这个全局节点依然会承受大量负载，推高响应延迟。

具体来说：

- 若每条事件都交给同一个 Session 处理：上下文最连续，但受单 ReAct Loop 串行执行上限约束，耗时长、吞吐低，多任务中间细节混杂。
- 若每条事件都新开独立 Session：并发最高，但缺全局上下文会让结果割裂，多个 Session 各自回复还会造成交互混乱。
- 折中方案（双层 + 订阅直通）让 Router 只做冷启动与跨任务协调，后续事件由程序直接发往对应 Worker。

## 核心决策

> 初始事件经由 Router 层创建 Worker 并建立订阅，同一 Thread 的后续事件直接发往该 Worker。

这是本设计的结论性语句，也是第 3.2 节图注原文。下文拆解其中的概念与运行机制。

## 关键概念

| 概念 | 含义 |
| --- | --- |
| **Router 层** | 常驻的全局路由层，承接所有入口的人类交互，负责任务分派与跨任务协调。不直接执行具体任务，甚至可不配备执行工具。充当全局序点（Sequence Point）、协调点和记忆。 |
| **Worker 层** | 由负责具体执行的会话组成，彼此上下文隔离，挂载完整执行工具，在独立上下文中专注单一任务。不直接与人类交互，只向 Router 汇报状态。 |
| **Thread（事件流）** | 同一条连续事件流。例如同一个 IM 话题、同一个 GitHub Pull Request、同一封往来邮件串下的连续事件。 |
| **订阅（Subscription）** | Worker 创建后直接订阅其对应的 Thread，从而收到该 Thread 上的后续事件。 |
| **Fast Path / Slow Path** | 事件路由的两条路径：已订阅事件走 Fast Path 直通 Worker；未订阅的新事件走 Slow Path 经 Router 判断与分派。 |

## 运行机制

```
                新事件到达
                     │
        ┌────────────┴────────────┐
        │ 该 Thread 是否已被订阅？  │
        └────────────┬────────────┘
        否（Slow Path）           是（Fast Path）
              │                        │
   Router 层判断 / 分派         程序直接发往已订阅的
   创建 Worker Session           Worker Session
   建立对该 Thread 的订阅              │
              │                 Worker 专注推进任务
              └──────────┬─────────────┘
                         │
                   Worker 向 Router 汇报
                   Router 统一向用户回复
```

两条路径的具体行为：

- **已订阅（Fast Path）**：同一 Thread 下的后续事件由程序直通已订阅的 Worker，无需 Router 层再次调用工具转发。若新事件超出当前任务范围，Worker 可取消订阅或交回 Router 层重新分派。
- **未订阅（Slow Path）**：Router 层仍可观测所有事件以掌握全局状态，但仅负责判断和分派尚未被订阅的新事件。

### Thread 与 Worker 是多对多

- 一个 Worker 可同时订阅多个相关 Thread。
- 同一个 Thread 也可被多个 Worker 订阅。
- 当多个 Worker 在同一工作环境或讨论中交集时，该 Thread 下的新事件会同时直通所有订阅它的 Worker，使它们无需点对点通信，也有机会获知彼此操作并自行解决冲突（例如多个 Worker 都订阅了同一个 PR 的 Thread，就会收到相同的事件通知）。

### 输出侧仍然收敛

尽管事件入口被分流，输出侧保持统一：Worker 仍将关键结论汇报给 Router 层，由 Router 层统一向用户回复并同步全局记忆，避免多个会话各自回复带来的混乱。

## 实证（来自原文第 7.1 节）

原文用约 300 条消息（约 20 条工作请求 + 闲聊/跟进/叫停/CI 消息）驱动端到端实验，对比四种方案。其中「去掉直通的 Super-agent」与完整版对比：

- 任务完成时间与完整版基本一致（直通不提高任务完成质量与速度）。
- 但 Router 需要做出的决定增加约 **30%**。
- 总读缓存 token 从约 **2323 万** 增加到 **3177 万**，增幅约 **37%**。

结论：在实验负载下，直通机制的价值在于**为 Router Session 节省可观的 token 与推理开销**，而非提升单任务质量或速度。

## 取舍与适用边界

- **规模扩大时的权衡**：当单个 Router Session 不足以承载，Router 层内部可做水平切分（Sharding）或多层过滤。切分粒度越细，并发吞吐越高，但分片间记忆与上下文连续性越低。在全局记忆问题被解决前，这一权衡始终存在。
- **批处理兜底**：Router 层在上一轮推理期间到达的事件会积压、下一轮一并处理（Batching），合并处理额外开销很小。因此一定范围内，拥堵越多，单决定分摊推理时间越低。这解释了为何即便去掉直通使 Router 峰值负载增加，也未触及单 Router 吞吐瓶颈（原文 7.2 节）。

## 与 MoonPub 的关联

MoonPub 当前是**同步 CLI**，没有常驻的 Router/Worker 运行时，也不存在 Thread 级别的事件流。因此本设计目前是**架构参考存档**，不是已实现的模块。

若未来 MoonPub 演进出以下形态，本机制可作为直接的路由范式：

- 一个常驻的 agent / daemon 模式，并发处理多个 Obsidian Inbox 素材、多个微信草稿或多条 CI 反馈；
- MCP server（`mcp/server.py`）从「每次调用独立执行」升级为「按会话/任务保持上下文并并发推进」；
- 把「单个 IM 话题 / 单个 PR / 单个邮件串」映射为 Thread，把「具体执行会话」映射为 Worker，把「统一入口与协调」映射为 Router。

届时落地的第一步建议：先只在新增的并发入口（而非现有 CLI 命令）引入 Thread→Worker 订阅表与 Fast/Slow Path 分流，保持 CLI 既有的确定性行为不变。
