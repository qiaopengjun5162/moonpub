# AI 协作协议：把工程当研究做

> 定位：这份文档记录「人与 Agent 共同开发」的协作纪律，不描述具体功能，只管**工作方式**。
> 与 [ENGINEERING_AGENT_GUARDAILS_ZH.md](ENGINEERING_AGENT_GUARDAILS_ZH.md) 的关系：那份管分支、提交、PR、生产边界等元规则；这份管**注意力该放在哪、什么不能被省**。

## 一、这份文档要解决的问题

Agent 让「实现」这一步变快了，但没有让规划、设计、判断、质控变快。

危险不在于有人主动决定偷懒，而在于：**手工实现原本是一道免费的、强制的设计自检**——写不下去，往往意味着还没想清楚。Agent 把这层摩擦削平之后，这道自检就默认消失了，必须被显式补回来。

另一个副产物更容易被忽略：**Agent 会让坏设计也能跑起来**。过去糟糕的架构常常连编译或基本流程都过不去，失败本身是警报；现在生成代码质量足够高，一个错误的设计前提也能被漂亮地实现成一个能运行的系统。于是「能跑」被误读成「设计对」。

结论：实现越顺滑，规划、设计、判断、质控这几段**单位价值反而越高**，不是越低。

## 二、四条原则与落地动作

### 原则 1：目标先行，指标可观测

开工前先写清三件事：目标是什么、用什么指标判断达成、什么算失败。

- **落地**：任务开始时先输出「目标 / 指标 / 完成态定义」，再动手。
- **反模式**：先写代码，事后才想怎么验证。

### 原则 2：评估方法本身是可证伪项

系统没达标时，诊断顺序**固定**为：

```
评估方法 → 环境 / 配置 → 系统本身
```

- **落地**：红灯出现时，先问「这个 gate 测的是对的东西吗」，再问「环境/依赖/权限对不对」，最后才动业务代码。
- **反模式**：看到红就先改代码，越改越乱。

### 原则 3：人类守设计与判断，Agent 扛实现

人类的注意力单位从「行」抬升到「意图与设计」；质量信任押在 gate 上，不押在「我读过每一行」。

- **落地**：人类负责目标定义、架构取舍、是否扩大范围、是否发布；Agent 负责批量实现与验证。
- **前提**：gate 必须可信，否则「快速确认」会退化成橡皮图章。

### 原则 4：省下的实现时间，定向投回不随规模缩水的环节

实现的加速不会自动把时间还给规划与设计，必须**显式再分配**。

- **落地**：每个任务收尾时问一句——「这次有没有因为写得快，而跳过了本该想清楚的事？」
- **反模式**：省下的时间被用来写更多实现，规划与判断反而更薄。

## 三、Gate 的可信度标准

一个 gate 值得信任，需要同时满足三条：

1. **见过它抓到真问题** —— 不是只见过它变绿；
2. **定期质疑它测的是不是对的东西** —— 门本身也是假设；
3. **全绿时仍保留一句追问** —— 绿了，但真的对吗？

只满足第 1 条，是「有测试」；三条都满足，才是「有验证机制」。

## 四、在 MoonPub 中的现成映射

| 原则 | 项目中的承载物 |
| --- | --- |
| 目标与指标 | `release-check` 聚合发布门禁；`preflight` 本地发布前质量门 |
| 评估可证伪 | CI 变红时，先分辨是 audit（依赖漏洞）、仓库权限，还是代码本身 |
| 人类守判断 | 版本漂移要不要修、范围要不要扩、PR 合不合、版本发不发 |
| 定向再投入 | 收尾阶段明确「不加新功能、不擅自扩范围」 |

## 五、反模式清单

- 用「Agent 很强」替代「规划想清楚了」
- 代码全绿就认为设计正确
- 看到 CI 红就直接改业务代码，不先分辨归因层
- 用 gate 的通过率替代对 gate 本身的审视
- 因为实现变快，就把省下的时间继续投入更多实现
