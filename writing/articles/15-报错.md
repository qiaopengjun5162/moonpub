> **项目**：MoonPub —— 用 Rust 写的公众号发布副驾驶
> **仓库**：github.com/qiaopengjun5162/moonpub

今天上午推一篇文章，屏幕上出现这么几行：

```text
Error: WeChat cookie session not ready: cookie 会话已过期或失效（跳转到了登录页），请先 `moonpub login` 重新扫码
  run 'moonpub login' to scan the QR code, then: moonpub push .../writing/articles/14-配图.md
```

我照最后一行扫了码，再敲一次，推上去了。整个过程没有打开文档。

这不是我记性好，是 MoonPub 的一个硬习惯：**每个报错都带「下一步敲什么」**。这篇把最常撞的五个故障列出来，你可以把它当速查表；撞上别的，先看报错最后一行。

## 先看这张表

| 你看到的现象 | 报错里那句话 | 敲什么 |
| --- | --- | --- |
| 昨天还能推，今天不行 | `WeChat cookie session not ready` | `moonpub login` |
| 刚改完稿，推上去还是旧版 | `rendered HTML is stale` | 加 `--render` |
| 预览里图片是空白框 | `image_links [fail]: 1 broken image link(s)` | 改图片路径，重跑 `preflight` |
| 排版全变了 | `invalid theme name` | 换回主题清单里的名字 |
| 标题发不出去 | `title exceeds WeChat 64-char limit` | 砍到 64 字以内 |

下面五个小节，每个都附真实输出。

## 一、会话过期：大约三天一次

公众号后台用 cookie 会话登录，**实测寿命三天出头**：11 月 22 日 22:46 扫码，11 月 25 日 19:24 还能推，11 月 26 日 00:27 就失效了。

失效后的报错长这样（就是开头那段）：

```text
Error: WeChat cookie session not ready: cookie 会话已过期或失效（跳转到了登录页），请先 `moonpub login` 重新扫码
  run 'moonpub login' to scan the QR code, then: moonpub push <你的文章>
```

`moonpub login` 会弹一个浏览器窗口显示二维码，你用手机微信扫一下就行。

**这里我错过一次：** 我第一次看到这句就去查网络、查代理，折腾了十分钟——其实第一行已经写明「跳转到了登录页」，就是没有登录态。

还有一个坑：**扫码窗口只等 120 秒**。窗口是脚本弹的，你可能正好在喝水；两分钟一到，它把已经打开的登录页关掉，下次还得从头来。今天我就这么连栽两次。

我给它留了个开关，扫码前先设一下：

```bash
MOONPUB_LOGIN_TIMEOUT_SECS=900 moonpub login
```

它会把等待拉到十五分钟，提示也变成 `Waiting up to 900s for WeChat backend login...`。不设也行，默认还是 120 秒——脚本里没人扫码时，等两分钟就够判断了。

## 二、产物过期：它宁可停下，也不推旧排版

改完 Markdown 直接推，可能撞这个：

```text
Error: rendered HTML is stale: .../writing/articles/zz-demo.html
  the Markdown is newer than the rendered HTML, so the draft would publish stale content
  re-render first: `moonpub render <article.md>` (`moonpub push` also accepts `--render`)
```

它的判断很朴素：**Markdown 的修改时间比 HTML 新，就拒绝联网**。因为推上去的是 HTML，你的改动只在 Markdown 里，读者看到的就是上一版。

按它说的加 `--render`：

```bash
moonpub push writing/articles/14-配图.md --render
```

`--render` 是**无条件重渲**，draft.json 已经存在也重渲，所以不存在「加了还在推旧产物」这条路。

## 三、图找不到：preflight 会点名

正文里的图片路径写错，渲染不会报错，推上去就是一个个空白框。所以在推之前跑一次检查：

```bash
moonpub preflight writing/articles/zz-demo.md
```

```text
    - image_links [fail]: 1 broken image link(s): .../assets/2026-11-26-images/没有这张.png
```

（真实输出里是完整的绝对路径，这里为了排版省掉了前半段。）

它把找不到的那张**逐个列出来**，你照着改路径就行。同一个检查还会告诉你封面在不在、摘要多长、标题多少字：

```text
    - cover [warn]: cover image missing; WeChat will use the first body image as the cover — run `moonpub cover <article> --screenshot`
    - digest_limit [warn]: digest empty; WeChat will auto-extract from content
```

`[warn]` 不妨碍推送，`[fail]` 会。图找不到是 `[fail]`，封面没做只是 `[warn]`——微信会拿正文第一张图当封面，丑但能发。

## 四、主题名拼错：不会静默回落

frontmatter 里主题名写错一个字：

```yaml
theme: 不是主题
```

```text
Error: invalid theme name: 不是主题
  run 'moonpub help render' or check [wechat] theme in moonpub.toml for valid names
```

这条报错以前是不存在的：拼错的名字会被悄悄当成默认主题，文章排版完全变了，你却在预览时才发现，或者更糟——`check --json` 告诉你「可以发」。现在它直接拦在渲染前。

主题清单看这张表就够了：

```bash
moonpub layout-recipes
```

里面还写着每套主题默认配哪个封面风格。

## 五、标题超长：64 字上限，报出实际字数

```text
    - title_limit [fail]: title exceeds WeChat 64-char limit (70 chars): 长长长长……
```

摘要的上限是 120 字，超了只是 `[warn]`——微信会自己截。标题超了是硬失败，因为折叠线在那儿，读者在信息流里只看到前一行。

**64 是按字符算的，不是字节。** 中文一个字算一个，所以「二十来个汉字」离上限还很远；真要撞上，通常是标题里塞了副标题、日期、系列编号。

## 卡住了怎么办

**先敲 `moonpub doctor`。** 它检查配置、文章目录、凭据，缺什么直接说，还会打印下一条命令。今天这类「不知道从哪下手」的时刻，它比翻文档快。

**想看本地状态，敲 `moonpub status`。** 草稿推没推、`media_id` 多少、下一步该敲什么，都在这儿。cookie 模式下 `list-drafts` 不可用（它要 AppSecret 凭据），本地视角就是 `status`。

**读报错只读三件事：** 第一行是什么坏了，第二行为什么，最后一行敲什么。MoonPub 的报错按这个顺序写，中间那些缩进是给要深挖的人看的。

## 下一步

报错处理完，回到正常流程：要把它推上草稿箱、在手机上过最后一遍，看「MoonPub 推草稿，后台那些开关它替你点完」；想知道图该做多大、哪张图在手机上会糊，看「MoonPub 文章里的图，怎么放才看得清」。
