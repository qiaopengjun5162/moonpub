> **项目**：MoonPub —— 用 Rust 写的公众号发布副驾驶
> **仓库**：github.com/qiaopengjun5162/moonpub
> **本篇**：第 1 篇 · 4967 行的第一个提交，和它埋下的那个 bug

## 前言

MoonPub 是一个用 Rust 写的命令行工具，解决一件很具体的事：把 Obsidian 里写好的 Markdown，变成一篇真正可发布的微信公众号文章。

它不替你发文。它做的是那些重复到让人厌烦的搬运：渲染排版、生成摘要、做封面、上传图片、创建草稿、配置原创/赞赏/留言/创作来源，然后**停下来等你确认**。最后那一下「发表」永远由人来点。

这篇文章讲这个项目的第一个晚上：我在一个空目录里，用一个提交塞进去 4967 行代码。四个月后，其中一个文件从 3286 行变成 131 行。

读完你能拿走两件事：一是「一次能跑通」和「结构正确」差多远，二是一个重复实现是怎么在四个月里悄悄藏住 bug 的——这个 bug 不是你猜的那种小问题，它让文章里的单引号直接破坏 HTML 属性。

## 背景

我平时在 Obsidian 里写作，写完发公众号。问题不在写，在「发」。

正文已经是 Markdown 了，但要变成一篇可发布文章，中间隔着这么一串动作：

```text
开后台 → 新建图文 → 粘贴正文 → 重新排版 → 上传图片 → 设封面
→ 声明原创 → 勾协议 → 开赞赏 → 开留言 → 选创作来源 → 选合集
→ 插模板 → 发手机预览 → 回后台确认
```

十几项设置，每项点几下，而且微信**不记得你上次的选择**，下次全部重来。

2026 年 6 月 10 日晚上 8 点 07 分，我决定把整条链路用 Rust 重写。那天晚上，我一个提交写完了六个模块。

## 摘要

| 项 | 内容 |
| --- | --- |
| 问题 | 公众号发布有十几项重复设置，无法用脚本复用 |
| 现象 | 第一个提交 4967 行，其中 `src/lib.rs` 一个文件 3286 行 |
| 根因 | 把「一次能跑通」当成「结构正确」，没有模块边界 |
| 修法 | 四个月内把单文件拆成 65 个文件，`lib.rs` 降到 131 行 |
| 结论 | 拆分时暴露：5 处 HTML 转义有 4 处漏转义单引号，第一个提交就把 bug 埋进去了 |

## 实操

### 步骤 1：看第一个提交到底写了多少

先确认这个数字不是我记错。查第一个提交的文件清单：

**输入**

```bash
git show --stat 5a8bed0
```

**输出**

```text
5a8bed0 feat: MoonPub CLI — WeChat publishing workflow in pure Rust
 .gitignore                 |    4 +
 Cargo.lock                 |  669 +++++++++
 Cargo.toml                 |    7 +
 PROGRESS.md                |  113 ++
 README.md                  |   81 ++
 docs/BROWSER_AUTOMATION.md |  169 +++
 scripts/moonpub-backend.sh |  287 ++++
 src/lib.rs                 | 3286 ++++++++++++++++++++++++++++++++++++++++++++
 src/main.rs                |   20 +
 src/wechat.rs              |  331 +++++
 10 files changed, 4967 insertions(+)
```

一个空目录，一个晚上，4967 行。

`src/lib.rs` 一个文件 3286 行，装了六件事：`render`（Markdown 转微信 HTML）、`push`（直调微信 API 建草稿）、`export`（导出 Zola 博客）、`preview`（本地打开）、`radar`（选题趋势）、`status`（状态跟踪）。

提交信息最后一行写着 `49 unit tests, 0 clippy warnings`。当时我觉得这是个很干净的起步。

### 步骤 2：看它现在的样子

四个月后，同一个文件：

**输入**

```bash
wc -l src/lib.rs
```

**输出**

```text
     131 src/lib.rs
```

3286 → 131。少了 3155 行。

剩下的去哪了？去了别的文件：

**输入**

```bash
find src -name "*.rs" | wc -l
find src -name "*.rs" -exec cat {} + | wc -l
git rev-list --count HEAD
git log --format=%s | grep -cE "^(fix|bugfix)"
```

**输出**

```text
65
29298
484
163
```

65 个文件，29,298 行，484 次提交，其中 163 次是修 bug。

**这张表里最该注意的是 163。** 三分之一的提交在修 bug——不是设计出来的架构，是撞在微信后台 DOM 上撞出来的。

### 步骤 3：拆分是从哪一天开始的

不是某次专门的重构，是第二天就开始了：

**输入**

```bash
git log --all --grep="extract radar" --format="%h %ad %s" --date=format:"%m-%d %H:%M"
```

**输出**

```text
728c530 06-11 17:13 refactor: extract radar.rs from lib.rs (-1270 lines)
```

第一个提交的第二天，一次砍掉 1270 行。

然后是 `protocol.rs`，然后是九月把 `protocol` 拆成目录。四个月里这件事一直在做，没有「重构周」。

### 步骤 4：拆的时候撞出一个活了四个月的 bug

这才是我写这篇的真正原因。

拆到渲染层时我发现，HTML 转义被实现了五遍。查当时的版本，看哪几份转了单引号：

**输入**

```bash
for f in src/cover.rs src/footer.rs src/illustrate.rs \
         src/markdown/blocks.rs src/markdown/inline.rs; do
  n=$(git show ff64d47^:$f | grep -c "&#39;")
  printf "%-28s 转义单引号: %s\n" "$f" "$n"
done
```

**输出**

```text
src/cover.rs                 转义单引号: 2
src/footer.rs                转义单引号: 0
src/illustrate.rs            转义单引号: 0
src/markdown/blocks.rs       转义单引号: 0
src/markdown/inline.rs       转义单引号: 0
```

五份实现，**只有 `cover.rs` 转了单引号，其余四份都是 0**。

这个 bug 的后果很直接：正文里出现单引号时，如果它落在 HTML 属性值里（比如图片的 `alt`、链接的 `title`），属性会被提前闭合，页面结构当场崩掉。而且它不报错，只是排版坏掉。

它从第一个提交活到了 `ff64d47`——四个月。

## 解释说明

### 为什么 3286 行的单文件是错的

它当时确实能跑。渲染通、推送通、导出通、49 个测试全绿、clippy 零告警。所以「能跑」这个标准，它满分。

但它错在三个地方，每个都在四个月里付了账：

**第一，定位成本。** 任何一个改动，都要在一个 3286 行的文件里找位置。这不是抽象的坏处，它会直接改变你的行为——你会开始倾向于「就在附近加一段」，因为跨文件重构在那个文件面前显得太贵。

**第二，没有边界，重复实现必然出现。** 这是最关键的一条。`render` 需要转义 HTML，`footer` 也需要，`illustrate` 也需要。当它们都在同一个文件里、又没有明确的模块边界时，最省事的做法就是再写一遍。

于是就有了五份。而五份实现必然分叉——`cover.rs` 那份是「更宽的」版本，作者当时记得单引号，另外四份的作者（也是我）没记。

**第三，测试只能测到最外层。** 3286 行的单文件，内部函数互相调用，你没法单独测一个片段。49 个测试听着不少，但都集中在公开入口。

### 为什么这个 bug 能活四个月

因为它不响。

单引号没被转义，HTML 不会报错，Rust 不会 panic，测试不会红。它只是在某些文章里，某个图片的 `alt` 属性把标签截断了，排版悄悄歪掉。

而我的测试断言的是「函数返回了什么字符串」，不是「渲染出来的 HTML 结构对不对」。所以五份实现里四份是错的，测试照样全绿。

**一条可迁移的经验**：当同一个逻辑在代码里出现第二份时，它已经不是「重复代码」问题了，它是一个**即将分叉的 bug**。第一份和第二份的差异，就是未来的故障点。

`ff64d47` 的修法是把五份合成一份——`src/html.rs:15` 的 `escape()`，单次遍历、五个字符全覆盖，并配一个测试直接断言：

```rust
assert_eq!(escape("a&b<c>d\"e'f"), "a&amp;b&lt;c&gt;d&quot;e&#39;f");
```

那个 `&#39;` 就是四个月前漏掉的东西。

## 验证

这篇文章里每个数字都能自己复算。四条命令：

```bash
# 1. 第一个提交的规模（4967 行 / lib.rs 3286 行）
git show --stat 5a8bed0

# 2. 现在的规模（131 行 / 65 文件 / 29298 行 / 484 提交 / 163 修复）
wc -l src/lib.rs
find src -name "*.rs" | wc -l
find src -name "*.rs" -exec cat {} + | wc -l
git rev-list --count HEAD
git log --format=%s | grep -cE "^(fix|bugfix)"

# 3. 首次拆分
git show --stat 728c530

# 4. 五份转义里四份漏单引号
for f in src/cover.rs src/footer.rs src/illustrate.rs \
         src/markdown/blocks.rs src/markdown/inline.rs; do
  echo -n "$f: "; git show ff64d47^:$f | grep -c "&#39;"
done
```

当前代码锚点（现在仓库里可直接看到）：

- `src/html.rs:15` —— 唯一的 HTML 转义实现
- `src/cover.rs:269`、`src/footer.rs:80`、`src/illustrate.rs:149`、`src/markdown/blocks.rs:203` —— 四个薄包装，全部转调 `crate::html::escape`
- `src/html.rs:1-8` —— 模块注释里就写着这段历史：「四个几乎相同的私有副本，加上 cover 里更宽的一个」

覆盖率那一篇会讲这 593 个测试怎么来的，以及为什么「覆盖率 72%」这个数字当时是假的。

## 总结

1. **「能跑通」不是结构验收标准。** 第一个提交能跑、测试全绿、lint 干净，但它错在把六件事挤进一个文件。验收要看的是：改一个功能要动几个文件、能不能单独测一个片段。
2. **重复实现是第一优先级的 bug。** 同一段逻辑出现第二份时，差异就已经在积累了。五份 HTML 转义分叉四个月，代价是四个月里所有带单引号的文章排版都是坏的。
3. **测试要断言可观察的结果，不是函数的返回值。** 断言 `escape()` 返回的字符串，测不出「HTML 结构是否完好」；断言渲染出的 HTML，才测得出。

下一篇讲第二天晚上发生了什么：三个半小时，87 次提交，为了点开微信后台里一个开关。
