2026-10-29 晚上，有人问我一句话：

> 测试覆盖率如何了，要验证的，不要写了很多没有验证大家都没有办法使用。

我当时心里是有底的——项目一直在跑 `cargo nextest`，几百个测试全绿，`lcov.info` 也在仓库里躺着。覆盖率嘛，两位数，看着还行。

直到我真的把 `cargo llvm-cov` 跑起来，逐文件看那份报告。

## 总数字 72%，但发布链路在裸奔

总量：**71.99% 行覆盖**，四舍五入 72.0%。

看起来及格。但把文件拆开看：

| 文件 | 作用 | 覆盖率 |
| --- | --- | --- |
| `src/wechat.rs` | 微信 API 客户端（取 token / 建草稿 / 传图 / 发布） | **40.1%** |
| `src/push.rs` | 推送管线（渲染→传图→建草稿→归档） | **43.6%** |
| `src/publish.rs` | 浏览器步骤编排 | **1.6%** |
| `src/publish_steps.rs` | 编辑器内单步操作 | 12.0% |
| `src/cdp.rs` | CDP 原语 | 24.1% |

**这个项目最核心的事——把文章推到公众号——它的主链路覆盖率是 40%、43%、1.6%。**

72% 是怎么来的？被大量解析函数、格式化函数、纯字符串处理平均出来的。那些代码确实被测了，测得很漂亮。但它们不是用户真正依赖的那条路。

更扎心的一个数字：`wechat.rs` 当时有 **15 个测试**，**没有一个调用过 `create_draft` 或 `upload_image`**。它们全在解析 JSON 字符串——喂一段假响应，断言解析结果对不对。

这叫测试吗？从行数上看，它确实执行了 `parse_response` 那几行。但它从来没碰过"发一个 HTTP 请求到微信"这件事。**测试写了很多，被测代码一行没跑。**

## 根因：出口是写死的

为什么测不到？因为 `WechatClient` 把域名硬编码在每一个方法里：

```rust
const DRAFT_ADD_URL: &str = "https://api.weixin.qq.com/cgi-bin/draft/add";
```

你要测 `create_draft`，它就必须真的往 `api.weixin.qq.com` 发请求。CI 里没有凭据、没有网络、更不该打真实微信后台。于是唯一"能跑"的测试方式，就是绕开这个方法，去测它内部调用的纯函数。

**问题的本质不是"测试写得少"，是"代码没有给测试留出口"。** 一个把外部地址写死在方法体里的客户端，天然不可单测。你写一百个测试也碰不到它。

## 修法：把出口变成数据

`c1c1286`（2026-10-29 22:14）做了一件事：把"往哪发"从常量变成字段。

```rust
pub fn new(appid: impl Into<String>, secret: impl Into<String>) -> Self {
    Self::with_base_url(appid, secret, default_base_url())
}

pub fn with_base_url(appid, secret, base: impl Into<String>) -> Self { … }

fn default_base_url() -> String {
    std::env::var("WECHAT_API_BASE")
        .ok()
        .map(|v| v.trim().to_owned())
        .unwrap_or_else(|| "https://api.weixin.qq.com".to_owned())
}
```

三行代码的改变，带来两个能力：

1. **测试可以指向本地 mock**：`WechatClient::with_base_url("app", "secret", mock.base_url())`
2. **staging 可以指向回放代理**：不用改一行生产默认值

配套新增 `src/mock_wechat.rs`——一个基于 `std::net::TcpListener` 的假微信服务。零外部依赖，按顺序应答，并且**记录收到的每一个请求**。这样测试断言的不是"函数返回了什么"，而是"真正发出去的 path 和 body 长什么样"。

举个现在的测试长什么样：

```rust
let mock = MockWechat::start([r#"{"errcode":0,"media_id":"MEDIA_1"}"#]);
let client = WechatClient::with_base_url("app", "secret", mock.base_url());

let id = client.create_draft("TOKEN", &draft)?;

assert_eq!(id, "MEDIA_1");
let req = &mock.wait_for(1)[0];
assert_eq!(req.path(), "/cgi-bin/draft/add");
assert!(req.body_text().contains("测试标题"));
```

这才叫验证：**请求真的发出去了，路径对了，body 里有该有的东西。**

## 顺手抓到的一个真 bug

改造过程中撞上一个之前完全没发现的问题。

`proxy_url_for` 的逻辑是：如果环境变量里有 `HTTPS_PROXY`，就给请求挂代理。听起来没问题——直到你把 mock 服务跑在 `127.0.0.1` 上。

本地请求也被塞进了代理，代理再往 `127.0.0.1` 转发，直接 502。测试全红，但红的原因不是代码错，是**本地回环地址被当成了外网**。

修复很短（`wechat.rs:409`）：

```rust
pub fn proxy_url_for(url: &str) -> Option<String> {
    if is_loopback_url(url) {
        return None;   // 本地服务一律绕过代理
    }
    …
}
```

这个 bug 之前一直存在，只是没人测过本地 mock，所以从没暴露。**可测性改造本身，就是一次代码体检。**

## 改完之后：真实的数字

`cargo llvm-cov nextest` 实测：

| 文件 | 修复前 | 修复后 |
| --- | --- | --- |
| `src/wechat.rs` | 40.1% | **93.6%** |
| `src/push.rs` | 43.6% | **70.9%** |
| `src/publish.rs` | 1.6% | 6.9% |
| 合计 | 72.0% | **74.2%** |

新增的测试不是"多写几个断言"，是三类真正跑代码的：

- **18 个客户端方法级测试**：直接打 mock，断言 path / body / 返回解析 / `errcode` 失败分支
- **5 个管线端到端测试**：`push_wechat_draft_with_client` 从磁盘文章一路走到归档——渲染 → 取 token → 传图 → 建草稿 → 写 `.media_id` → 移目录
- **5 个纯函数测试**：`xpath_literal` 处理名字里带 `'` 或 `"` 的账号（XPath 没转义字符，只能拼 `concat`）

还有一次**真实二进制冒烟**（不是测试代码，是拿 release 二进制打 python mock）：

```bash
moonpub new "端到端验证"
moonpub render "Articles/drafts/端到端验证.md"
WECHAT_APPID=… WECHAT_SECRET=… WECHAT_API_BASE=http://127.0.0.1:18878 \
  moonpub push "Articles/drafts/端到端验证.md"
```

mock 依次收到 `GET /cgi-bin/token`、`POST /cgi-bin/draft/add`，输出 `media_id: MEDIA_E2E`，`.media_id` 落盘，`status.jsonl` 记 `ready`。

这次冒烟还顺手暴露了另一件事：CLI 走到浏览器那一步时**真的连上了线上后台**，列出了 10 篇历史草稿——因为 mock 草稿在真实后台不存在，最后报 `draft list edit button not found`。这恰好印证了下一节。

## 有些代码，本来就不该假装覆盖

`publish.rs`（1.6%→6.9%）、`publish_steps.rs`（12.0%）、`cdp.rs`（24.1%）、`push_browser.rs`（22.2%）——加起来约 2700 行浏览器自动化，覆盖率在 **7%–27%** 之间。

我没有去把它们"刷"上去。因为它们靠 CDP 操作真实微信编辑器，代码里就有人机确认点：

```rust
wait_enter();
ask_ok("选中…了？");
```

这些不可能在 CI 里跑。硬写单测只会得到一堆"调用了一个 mock 过的空函数"的假测试，数字好看，问题一个不少。

所以 `docs/TEST_COVERAGE_ZH.md` 里把这条边界写死了：

> 真正发布到公众号的浏览器自动化部分：7%–27%，这不是遗漏，而是无法用单元测试验证，只能人工过闸。

人工过闸的入口是 `moonpub step-test` / `test-zanshang` / `test-chuangzuo` / `test-yulan`，发版前必须人看着跑一遍。**覆盖率不能替代它。**

## 门槛：73%

`scripts/coverage.sh` 设了行覆盖下限 **73%**（实测 74.2% / CI 74.19%，留平台漂移余量）。规则三条：

- 只升不降，涨了就抬门槛
- 不许为了让红灯变绿而下调门槛，真要下调必须在 PR 里说明原因
- **新增微信 API 端点必须同时加一条打 mock 的测试**，否则这个端点等于没验证

最后一条是这次改造真正的收获：它把"可测"变成了准入条件，而不是事后补救。

## 带走的一句话

> 覆盖率是平均值，平均值会骗人。真正要问的不是"总共多少"，而是"用户最依赖的那条路，覆盖率是多少"。
