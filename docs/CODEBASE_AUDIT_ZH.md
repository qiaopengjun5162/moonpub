# MoonPub 源码审计

这份文档不是愿景，也不是用户教程。

它只回答一个问题：

**基于当前真实源码，MoonPub 现在到底长成了什么样，下一步最该收什么，不该再散到哪里。**

## 审计范围

本轮审计主要基于这些真实入口和实现：

- `src/cli.rs`
- `src/app.rs`
- `src/intake.rs`
- `obsidian-plugin/main.ts`
- `.github/workflows/build.yml`
- `.github/workflows/release.yml`

同时参考当前已经存在的用户侧和产品侧文档，但判断优先以源码和验证链路为准。

## 一句话结论

MoonPub 当前已经不是“一个能推公众号草稿的小 CLI”。

更准确地说，它已经长成了：

- 一个以 Rust CLI 为核心的本地发布内核
- 两条正式输入工作流已经落地：飞书秒记、照片素材
- 一个正在形成正式首页的 Obsidian 插件入口
- 一层开始稳定下来的 JSON 协议，供插件 / App / Agent 复用

但同时，它也出现了一个非常明确的新阶段问题：

**编排层正在变重，入口层正在变大，如果现在不主动收架构边界，后续功能越多，维护成本会明显上升。**

## 当前最硬的源码证据

### 1. CLI 已经不是薄壳

`src/cli.rs` 当前约 `1709` 行。

这说明它已经不只是“解析几个命令”的薄入口，而是同时承担了：

- 多条工作流命令的解析
- `--preview` / `--no-open` / `--push` 组合约束
- 飞书与照片输入源的参数规则
- 帮助文本和错误边界

这本身不是坏事，但说明 MoonPub 现在已经进入“命令面宽、语义开始复杂”的阶段。

### 2. `app.rs` 已经是当前最重的编排中心

`src/app.rs` 当前约 `1100` 行，其中包含较多 app 级行为测试；生产路由本身已开始按本地文章、草稿 follow-up、微信发布等稳定边界下沉。

从源码看，它现在仍然承担：

- CLI 命令路由
- 输入工作流编排
- 本地渲染 / 预览串联
- `push` 后续动作编排
- 一批 app 级测试

上一轮审计最需要注意的一点已经部分收口：

`workspace_json`、`status_json`、`check_json`、`draft_from_inbox_json`、`intake_draft_preview_json`、`layout_audit_json`、`layout_recipes_json` 等结构化输出已经明显迁到 `src/protocol.rs`。

这说明协议层已经不再主要塞在 `app.rs` 里；当前剩余风险变成了协议模块继续长大后，需要保持字段一致性和 app 级行为测试，而不是让 builder 回流到编排层。2026-07-11 起，命令是否提供专属 JSON 由 `Command::has_structured_json_output` 在 CLI 模型层声明，`app.rs` 不再维护第二份命令白名单。

### 3. 输入模型开始统一，但还在继续长

`src/intake.rs` 当前约 `950` 行。

从这份文件可以确认两件好事：

- 飞书与照片已经不再是完全独立的“临时特例”
- `InboxMetadata` 已经开始承接统一输入模型

这是一条对的路，因为它把：

- `source`
- `status`
- `type`
- `external_id`
- `source_title`
- `captured_at`

这些输入源共有字段统一起来了。

但问题也很明显：

`intake.rs` 现在已经同时容纳了飞书搜索/拉取、照片批处理、frontmatter 生成、幂等复用和素材稿生成逻辑。后面如果再加语音、微信读书或更多来源，这里会继续变成大文件。

### 4. Obsidian 插件已经从“命令壳”长成了真实入口

`obsidian-plugin/main.ts` 当前约 `968` 行。

这份文件已经说明插件不再只是几个命令按钮：

- 有工作区首页工作台
- 有当前文章工作台
- 有飞书结果工作台
- 有上下文感知推荐
- 有首次建议步骤
- 有草稿打开 / 检查 / 预览 / 继续推进等后续动作

所以现在再把它称作“只是实验插件”已经不准确了。

更准确地说，它已经是：

**MoonPub 当前最像产品入口的一层。**

### 5. 测试与 CI 对核心 Rust 主干是有力的，但对插件入口仍然偏弱

从源码和 workflow 可以确认：

- Rust 主干有大量模块内测试
- CI 已跑 `fmt` / `clippy` / `cargo nextest`
- Windows smoke 已覆盖无凭证基础路径
- release workflow 也在验证打包资产

这说明：

- CLI 主干质量约束已经不算弱
- 发布资产链路也开始被认真约束

但插件这边目前还只有：

- 本地 `npm run build`
- 说明文档
- 真实人工使用证据待补

也就是说，插件已经开始承担“产品入口”角色，但它的自动化验证强度还没有跟上这个定位。

## 当前产品结构判断

基于源码而不是愿景，MoonPub 当前其实已经形成了三层：

### 第一层：Core

核心是 Rust CLI 和发布主链路。

包括：

- 渲染
- 预览
- 推送
- 浏览器自动化
- 文章状态
- 导出

### 第二层：Input Workflows

当前已经正式存在：

- 飞书秒记
- 照片素材

后续明显会继续长：

- 语音笔记
- 微信读书 / 摘录

### 第三层：User Surfaces

当前已经正式存在：

- CLI
- Obsidian 插件

后续可能继续长：

- 本地 App
- Agent 封装

这个三层结构现在不是“应该这样想”，而是“代码已经开始这样长了”。

## 当前最关键的结构性风险

### 风险 1：`app.rs` 会继续变成总控大文件

这是当前最明显的工程风险。

如果后面继续往里面加：

- 新输入源
- 新 JSON 协议
- 新工作流分支
- 新插件入口动作

那 `app.rs` 会越来越像“所有事都能做，但没人敢动”的中心文件。

### 风险 2：协议层已经存在，但还没真正模块化

`workspace --json`、`status --json`、`check --json`、`layout-recipes --json`、`layout-audit --json`、`draft-from-inbox --json`、`intake ... --draft --json` 已经说明：

MoonPub 现在已经不是只给人读终端文本的工具了。

这些输出已经开始集中到 `src/protocol.rs`，但仍主要是手写 JSON 字符串，而不是 serde 结构体。

这会带来三个问题：

- 协议演进成本高
- 字段一致性容易靠测试兜底而不是靠类型系统兜底
- 插件 / App / Agent 越依赖它，协议层越应该更稳定

### 风险 3：插件已经承担首页角色，但还缺对应级别的验证

这不是说插件做得不好，而是说：

**插件的重要性已经提升了，验证手段还没同步提升。**

当前它已经承担：

- 首页
- 工作流入口
- 结果页
- 下一步引导

但还没有：

- 插件层自动化交互测试
- 首页级真实使用证据归档
- 更明确的发布/回归清单

### 风险 4：输入源会继续加，但 `intake.rs` 的边界还没提前收

飞书和照片都已经证明“把来源素材先接进 Inbox，再走草稿/预览/推送”是对的。

也正因为这条路是对的，后面新输入源只会继续加。

所以现在最该提前做的不是“多加几个来源”，而是：

- 把输入源的共性协议抽清楚
- 把来源特有逻辑和共有编排再分干净一点

## 当前最值得做的 3 件事

### 1. 继续把协议层类型化

这是当前最值得做的工程收口。

不是为了抽象而抽象，而是因为：

- `workspace` / `status` / `check` / `layout-recipes` / `layout-audit` / `intake` 这些 JSON 输出已经开始被插件或 Agent 当接口用
- 它们已经不是一次性字符串
- 协议层稳定性会直接影响插件、未来 App 和 Agent

优先方向：

- 保持 `src/protocol.rs` 是唯一协议 builder 入口
- 后续如果协议继续增多，再考虑让 JSON 输出走结构体而不是手写字符串
- 不要把协议 builder 重新塞回 `src/app.rs`

### 2. 把 `intake` 层继续明确成正式模块

这件事和用户目标高度一致。

因为用户现在最关心的，已经不只是“写好的文章怎么发”，而是：

- 飞书怎么进来
- 照片怎么进来
- 后面其它素材怎么进来

优先方向：

- 继续固定统一 Inbox 元数据
- 明确来源特有逻辑和共有编排边界
- 减少新输入源继续把 `intake.rs` 做成总集线器

### 3. 补插件首页与首次体验证据

现在项目最大的产品优势之一，是“已经开始有入口”。

所以最值得补的不是再讲一次愿景，而是补：

- 首页截图
- 飞书入口 walkthrough
- 照片入口 walkthrough
- 当前文章入口 walkthrough

因为这会直接影响：

- 用户会不会用
- 我们能不能更真实地做下一轮评估
- 后续想包装成 Agent / App 时有没有可靠演示链路

## 关于“飞书是否单独拆项目”的当前判断

基于现在的源码状态，结论仍然不变：

**现在不适合拆仓库，更适合继续作为 MoonPub 内部正式模块推进。**

原因不是概念上的，而是代码层面的：

- 飞书链路当前仍然强依赖 MoonPub 的草稿、预览、推送和状态协议
- 现在真正开始形成价值的是“输入源 + 发布内核 + 入口层”的组合，而不是飞书单点本身
- 现在拆仓库，会先增加同步成本，不会先提升用户可用性

## 关于“是否适合包装成 Agent 产品”的当前判断

基于现在的源码状态，这个方向是可行的，但应该这样理解：

**不是重新做一个全新 Agent 项目，而是继续把 MoonPub 稳定成 Agent-ready 的本地发布内核。**

因为现在最像 Agent runtime 的，已经不是想象，而是现有代码：

- `workspace --json`
- `status --json`
- `check --json`
- `draft-from-inbox --json`
- `intake feishu ... --draft --json`
- `intake photos ... --draft --json`

所以更合理的路线是：

1. 继续稳定协议层
2. 继续稳定输入工作流
3. 继续强化插件首页这类用户入口
4. 在此基础上再长出 App / Agent 外壳

## 当前最实际的下一步

如果只看眼前最值得继续做的一小步，我建议是：

1. 继续补一份“首次体验真实证据”归档
2. 然后继续把 `src/protocol.rs` 的协议输出往类型化和一致性测试收

前者解决“用户不会用”的问题，后者解决“后面越做越重”的问题。

这两件事一前一后，正好对应这个项目当前最核心的两类目标：

- 产品收口
- 工程收口

## 审计后续进展

基于这份审计，当前已经开始落地两步工程收口：

1. `workspace` / `status` / `check` / `preview` / `push` / `draft-from-inbox` / `intake ... --draft` 的结构化输出 builder 已开始从 `src/app.rs` 抽到 `src/protocol.rs`
2. `IntakeFeishu`、`IntakePhotos`、`DraftFromInbox` 三条链路重复的“草稿后 preview / push / JSON / 文本收尾逻辑”已开始收成共用 helper

这说明当前项目已经不只是“识别出风险”，而是在沿着审计结论真实收工程边界。

本轮又继续往前收了一步：

3. `src/app.rs` 中重复的配置加载、飞书 source 分派，以及 `step-test` / `test-zanshang` / `test-yulan` / `test-chuangzuo` 这组同形态微信后台自动化入口，已经继续收成私有 helper；`app.rs` 文件长度也从上一轮审计时的约 `983` 行降到约 `910` 行

这一步的意义不是“代码更漂亮”而已，而是继续把 `run()` 往“命令路由器”方向推，减少后续再加输入流或自动化步骤时，把同一类编排细节重新复制回主入口的概率。

4. `Push` / `Publish --target wechat-draft` / `Preview` 这组三个命令分支里的命令层包装，也已经继续收成共用 helper；这样 `app.rs` 里的发布主线开始更清楚地区分“命令路由”与“微信草稿/本地预览具体包装”两层责任

这一步的价值在于，它继续压缩了 `run()` 里那种“只有一点点差别、但每个分支都手写一遍”的结构。后面如果继续扩 target 或补更多 app 级命令，复用点会更稳定。

5. `Render` / `Cover` / `Humanize` 这组三个文件型命令，也已经继续下沉为私有 helper；其中“先读取文章、就地 humanize 再写回”的文件读写逻辑被收成了共用函数，不再在 `render --humanize` 和独立 `humanize` 命令里各写一份

这一步的价值不是追求“每个命令都拆 helper”，而是优先把同一类文件型命令里的共享文件操作边界收清楚。这样后面如果继续扩类似命令，`run()` 会更稳定地只负责分发，而不是重新展开文件系统细节。

6. `src/app_support.rs` 已经开始作为 `app.rs` 的内部编排辅助层落地：前面几轮收出来的 helper 和命令级上下文 struct，不再只是“还留在同一个文件里”，而是已经真实迁出到独立模块。`src/app.rs` 也因此从约 `1027` 行降到约 `688` 行

这一步很关键，因为它意味着这轮收口终于跨过了“视觉上看像拆分，实际上还在同一个大文件里”的阶段。现在的 `app.rs` 更接近真正的命令路由层，后面如果还要继续收工程边界，重点会从“先把 helper 挪出去”转到“哪些编排该继续升成独立模块，哪些应该停在 `app_support`”。

7. `draft follow-up` 已经从 `src/app_support.rs` 继续拆成独立的 `src/app_draft_follow_up.rs`：`draft-from-inbox` 和 `intake ... --draft` 这类“草稿生成后如何 preview / push / 返回 JSON / 返回文本”的收尾逻辑，不再和 render/preview/push/publish 包装混在一个协调层里

这一步说明当前工程收口已经从“先拆出协调层”进一步进入“协调层内部继续按稳定行为边界细分”的阶段。后面如果还要继续拆，判断标准就很明确了：只拆那些已经形成稳定行为组合、并且在用户工作流里有清楚语义边界的内部编排。

8. 首次体验证据这条线，也已经从“只有一份清单”推进到“仓库里有固定归档位”：`docs/first-run-evidence/` 下已经明确分出 `homepage/`、`feishu/`、`photos/` 三个目录，并各自保留最小说明文件

这一步的价值在于，它把“后面要补真实截图和录屏”从一句口头 TODO 变成了可以持续落文件、持续复查、持续引用的仓库结构。这样后面无论是插件首页、飞书路径还是照片路径的首次体验证据，都不会再散落在临时目录和聊天记录里。

9. `src/app_support.rs` 现在又继续变薄了一层：本地文章命令包装已经拆到 `src/app_article_commands.rs`，微信发布命令包装已经拆到 `src/app_publish_commands.rs`

这一步的价值不在于“文件数变多”，而在于 `app_support` 终于不再同时承担“本地文章命令”和“微信发布命令”两类不同语义的包装。后面如果继续收口，判断会更简单：优先看有没有稳定命令边界，而不是继续往一个中间协调层里堆 helper。
