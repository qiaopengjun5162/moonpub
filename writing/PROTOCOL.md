# 记录协议

这份协议只解决一个问题：**让三个月后的自己，或者一个完全没参与的人，能复现你当时看到的东西。**

## 一、什么时候记

在操作发生的**同一段时间里**记，不要晚上补。

晚上补的必然结果是只剩结论。而结论是最不值钱的部分——AI 能生成结论，只有过程不能。

具体时机：

- 跑完一条重要命令、看到非预期输出 → 立刻记
- 一个 bug 修好了 → 立刻记，趁你还记得错的那一版长什么样
- 决定换方案 → 立刻记，写下"为什么原来那个不行"
- 发布、合并、CI 转绿 → 记一行，附 run id

一次记录 3 到 5 分钟。写不动就先写三行，回头补。

## 二、六要素

每一次操作，这六件事必须齐。缺哪一项，这项就是"没记"。

### 1. 意图：我本来想干什么

一句话，用动词开头。

> 想给 `WechatClient` 加一个可注入的 base URL，让测试不用打真微信。

不要写"优化代码"这种。优化什么、为什么现在优化，要说清。

### 2. 输入：我给出去的东西

- 涉及哪些文件、哪些命令
- 关键代码片段（只贴改的那几行，不要贴整个文件）
- 前提条件（比如"本机 shell 已导出 WECHAT_APPID"）

前提条件特别重要。本轮就有一次因为漏记这个，本地绿、CI 红，查了两轮。

### 3. 输出：实际发生了什么

**原样贴，不要复述。**

```text
test result: FAILED. 590 passed; 3 failed
```

而不是"测试基本通过，有几个失败"。差几个、哪几个，是两件完全不同的事。

长输出截取关键行。报错就贴报错原文，包括那串看起来没用的 `error[E0061]`。

### 4. 解释：为什么会这样

这一步是记录和日志的分水岭。日志说"发生了什么"，记录要说"为什么"。

> 18 个测试里 3 个 panic，因为 `create_draft` 里域名是常量，测试只能验 JSON 字符串，拿不到真实请求。

解释允许是错的。**错的解释也有价值**——它记录了当时的认知边界。后面发现推翻了，回来补一句"实际是 XX"就行，别删。

### 5. 问题：卡在哪

把卡点单独拎出来，一句话写清现象。

> 本地打 `127.0.0.1` 的请求被 `HTTPS_PROXY` 劫持，返回 502。

卡点值得单独立项，因为读者最想抄的就是这一段。

### 6. 证据：凭什么这么说

至少一条，能独立验证：

- 提交号：`c1c1286`
- CI run：`40893397135`
- 命令：`cargo llvm-cov nextest --summary-only`
- 截图路径
- 一行可复现的命令

没有证据的结论，在 `articles/` 里不能用。

## 三、截图怎么留

截图是唯一能证明"我确实在屏幕上看到过"的东西，也是文章里最抓人的部分。但截图最容易泄露信息，也最容易变成一堆不知道是什么的 PNG。

### 什么时候截

只截这四种，别多：

1. **失败现场**：红色报错、CI 红叉、panic 栈
2. **修复前后对比**：同一个页面/同一段输出的 before/after
3. **真实产物**：生成的 HTML、手机预览、微信后台草稿列表
4. **关键决策点**：两个方案的分叉、一个配置项的实际位置

不要截：成功后的绿色对勾（一张够了）、代码编辑器全屏、任何带账号信息的后台。

### 文件命名

```text
assets/YYYY-MM-DD-主题-序号-说明.png
```

例：

```text
assets/2026-10-29-coverage-01-before-72pct.png
assets/2026-10-29-coverage-02-after-74pct.png
assets/2026-10-29-mock-api-01-draft-add-request.png
```

主题用小写连字符，不用中文，避免跨平台路径问题。

### 截图后立刻做的事

在当次记录里写一行：这张图证明了什么。

```text
![推送成功](assets/2026-10-29-mock-api-01-draft-add-request.png)
—— mock 收到 POST /cgi-bin/draft/add，返回 MEDIA_E2E，证明请求确实发出去了。
```

没有这一行，三个月后你自己也不知道这图在说什么。

## 四、命令要记到能复制

记命令的粒度标准：**别人复制粘贴就能跑**。

不合格：

```text
跑了覆盖率
```

合格：

```bash
env -u WECHAT_APPID -u WECHAT_SECRET cargo llvm-cov nextest \
  --config-file /tmp/nextest-fast-timeout.toml --summary-only
```

本机跑和 CI 跑环境不一样时，两个都要记，并且写明差异。

## 五、归档位置

| 内容 | 放哪 |
| --- | --- |
| 一次具体操作 | `writing/operations/YYYY-MM-DD-短标题.md` |
| 一个阶段的总览 | `writing/chronicle/INDEX.md` 对应小节 |
| 给读者看的成稿 | `writing/articles/NN-标题.md` |
| 截图/录屏/终端文本 | `writing/assets/` |
| 可复用的工程教训 | `docs/ENGINEERING_LESSONS_ZH.md`（用它的模板） |

一次操作如果既产生了文章素材，又产生了通用教训，两处都写。教训面向"以后不重犯"，素材面向"以后写文章"。

> 区分标准：下一件事会不会因为这条记录而做得不一样？会 → 教训。不会，但讲出来有意思 → 素材。

## 六、脱敏红线

提交前逐条过一遍。任一条中了，就不要提交，或者裁掉重截。

- `AppSecret`、`access_token`（连 `?access_token=` 这种 query 也算）、`publish_id`
- cookie、`pass_ticket`、`uin`、`ticket`、session 文件内容
- 二维码（个人号、群、登录码都算）
- 手机号、微信号、真实姓名（除作者本人）
- 微信后台的敏感 URL（含 `token=`、`ticket=`）
- 服务器 IP、内网地址、SSH 配置

CLI 输出里出现过 token 的，截图前先跑一次不带 `--debug` 的版本，或者直接贴裁剪后的文本。

排障日志如果必须带 token 才能说清问题，用占位替换：

```text
access_token=REDACTED
```

## 七、三个反例

**反例一：把日志当记录**

> 2026-10-29：修了 push 的顺序问题，测试全过。

问题：修了什么顺序？原来什么样？为什么错？读者一无所获。

**反例二：只记结论**

> 结论：`draft: true` 会导致 release-please 找不到 latest release，改成 `false`。

问题：这是结论不是过程。怎么发现的？看的是哪条日志？试错了几次？没这些，读者下次遇到同类问题还是不会查。

**反例三：美化失败**

> 重构后测试全部通过，顺利提交。

问题：真实情况是 CI 红了两次，两次都是自己引入的回归。把这段抹掉，文章就从"经验"退化成了"宣传"。

## 八、记录骨架生成

```bash
./scripts/journal.sh "覆盖率实证"        # 生成今天的记录骨架
./scripts/journal.sh --list              # 看已有记录
```

脚本只生成骨架和当天已有的提交列表，内容还是要你自己填。它省掉的是"新建文件 + 敲日期 + 翻 git log"这几步摩擦，不是思考。
